# Online research: WebGL2 2D UI rendering, prior art, techniques, perf monitoring, layout

Scope: input for a backend-agnostic spec of a layered 2D UI renderer (TypeScript on WebGL2, browser + Electron) that mirrors an existing C++/OpenGL implementation. Every claim below carries the URL it came from. Where a source was only partially readable (403s, summarized pages) that is noted. Date of research: 2026-09-07.

Conventions: "WebGL2" means the Khronos WebGL 2.0 spec (OpenGL ES 3.0 based). "Desktop GL" means OpenGL 3.3/4.x core profile. Quotes are verbatim from the cited page unless marked paraphrase.

### A.2 Timer query support status (EXT_disjoint_timer_query_webgl2)

- Extension text: "This extension provides the same functionality as EXT_disjoint_timer_query. The IDL, description, and extension name are specialized for WebGL 2.0". API: `beginQuery(ext.TIME_ELAPSED_EXT, q)` / `endQuery`, `queryCounterEXT(q, ext.TIMESTAMP_EXT)`, `getParameter(ext.GPU_DISJOINT_EXT)`, `getQueryParameter(q, QUERY_RESULT_AVAILABLE)`; results "only become available at certain well-defined times" (after returning to the event loop). Last modified June 2023, extension #33. https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/
- Chrome: "Starting in Chrome 65, the EXT_disjoint_timer_query and EXT_disjoint_timer_query_webgl2 WebGL extensions have been disabled" and "will be re-enabled with sufficiently reduced precision to mitigate GLitch attacks" once Site Isolation shipped. https://www.chromium.org/Home/chromium-security/ssca/ . MDN BCD: WebGL2 variant Chrome 70+ (also 56 to 62), Edge 80+, Firefox: no, Safari: no. The WebGL1 variant in Chrome 70+ is "Only supported on macOS." https://github.com/mdn/browser-compat-data/blob/main/api/EXT_disjoint_timer_query_webgl2.json and https://github.com/mdn/browser-compat-data/blob/main/api/EXT_disjoint_timer_query.json . A 2021 chromium-discuss thread confirms it "seems to work without the flag enabled" in Chrome stable. https://groups.google.com/a/chromium.org/g/chromium-discuss/c/B9zBnC96t0I
- Firefox: gated behind a pref that defaults to false. Source: `WebGLExtensionDisjointTimerQuery::IsSupported` starts with `if (!StaticPrefs::webgl_enable_privileged_extensions()) return false;` (https://github.com/mozilla/gecko-dev/blob/master/dom/canvas/WebGLExtensions.cpp) and `webgl.enable-privileged-extensions` has `value: false` (https://github.com/mozilla/gecko-dev/blob/master/modules/libpref/init/StaticPrefList.yaml). Firefox exposes it under the WebGL1 name on both context types (only `EXT_disjoint_timer_query` appears in https://github.com/mozilla/gecko-dev/blob/master/dom/canvas/WebGLContextExtensions.cpp).
- Safari: off by default; "can be enabled in Safari 17.1" via a feature flag (https://github.com/mdn/browser-compat-data/issues/21351). stats-gl: "To support GPU monitoring on Safari you need to enable Timer Queries under WebKit Feature Flags > WebGL Timer Queries." https://github.com/RenaudRohlinger/stats-gl
- Practical constraints from figma/webgl-profiler: only `TIME_ELAPSED` scopes, no nesting of active queries, "There's no way to ask for a timestamp" in practice, some GPU/driver combos crash; "This currently only works in Desktop Chrome >= 70." https://github.com/figma/webgl-profiler
- Consequence: in Electron (Chromium) timer queries are available; in the browser build treat them as optional and gate the GPU-time panel on `getExtension` returning non-null and `GPU_DISJOINT_EXT` being false for the frame.

### A.3 GLSL ES 3.00 vs desktop GLSL: things that bite a port

- First line must be `#version 300 es` ("THIS HAS TO BE THE FIRST LINE! No comments and no blank lines before it are allowed."); `attribute`/`varying` become `in`/`out`; `texture()` replaces `texture2D()`; no `gl_FragColor`, declare `out vec4`. https://webgl2fundamentals.org/webgl/lessons/webgl1-to-webgl2.html
- Precision: "The fragment language has no default precision qualifier for floating point types" (GLSL ES 3.00 §4.5.4, https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf). Vertex defaults are `precision highp float; precision highp int;`. Minimum ranges: lowp 9-bit, mediump 16-bit (float range ±2^14), highp 32-bit; query `gl.getShaderPrecisionFormat(gl.FRAGMENT_SHADER, gl.HIGH_FLOAT)` and expect real 16-bit `mediump` on mobile (1000*1000 overflows mediump). https://webgl2fundamentals.org/webgl/lessons/webgl-precision-issues.html . Use `highp float` in the fragment shader for SDF math in pixel units (screen coordinates exceed mediump range at 16384).
- No `double`, no `dvec`, no 64-bit ints (not in GLSL ES 3.00 at all).
- Sampler arrays: "Samplers aggregated into arrays within a shader (using square brackets [ ]) can only be indexed with constant integral expressions" and issue 12.29 "RESOLUTION: Dynamic indexing of sampler arrays is now prohibited by the specification." (GLSL ES 3.00 §4.1.7 and §12.29). Ken Russell on public_webgl: implementations "should be doing a better job of rejecting this construct on all platforms"; workaround is "a switch statement and using a constant index into the array in each arm". https://www.khronos.org/webgl/public-mailing-list/public_webgl/1907/msg00004.php . This is what PixiJS does for its multi-texture batches ("Sprites can be batched with up to 16 different textures (dependent on hardware)", https://pixijs.com/8.x/guides/concepts/performance-tips). A `TEXTURE_2D_ARRAY` avoids the switch entirely for same-size atlas pages.
- Dynamic indexing: issue 12.30 "RESOLUTION: Mandate support for dynamic indexing of arrays except for sampler arrays, fragment output arrays and uniform block arrays." So uniform arrays and UBO members may be indexed dynamically in both stages (the GLSL ES 1.00 Appendix A fragment-shader restriction is gone). Same PDF.
- Derivatives: `dFdx`, `dFdy`, `fwidth` core (OES_standard_derivatives promoted), "must return 0 when evaluated inside" non-uniform control flow contexts per §8.9 note. `gl_FragDepth` core. https://webgl2fundamentals.org/webgl/lessons/webgl1-to-webgl2.html and the GLSL ES 3.00 PDF.
- Texel offsets must be compile-time constants within `MIN/MAX_PROGRAM_TEXEL_OFFSET` or compilation must fail. https://registry.khronos.org/webgl/specs/latest/2.0/#webgl_gl_differences
- `GL_FRAGMENT_PRECISION_HIGH`: the 3.20 spec says "The built-in macro GL_FRAGMENT_PRECISION_HIGH is defined to one" (https://registry.khronos.org/OpenGL/specs/es/3.2/GLSL_ES_Specification_3.20.html); in 3.00 the text extracted from the PDF does not mention the macro, so gate on `getShaderPrecisionFormat` rather than the macro.
- Shader compile-status polling is a sync stall: "querying compile status is a synchronous call, which breaks pipelining"; check `LINK_STATUS` only after linking, and prefer `KHR_parallel_shader_compile` where present. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices

### A.4 Premultiplied alpha and canvas compositing

- Spec: `alpha` "If the value is true, the drawing buffer has an alpha channel for the purposes of performing OpenGL destination alpha operations and compositing with the page"; `premultipliedAlpha` "the page compositor will assume the drawing buffer contains colors with pre-multiplied alpha"; `drawingBufferFormat` is "Initially RGBA8 or RGB8 for alpha:true and alpha:false respectively". `toDataURL` on a premultiplied context de-multiplies ("Note that this operation is lossy"). https://registry.khronos.org/webgl/specs/latest/1.0/
- "The browser defaults to compositing a WebGL canvas using premultiplied alpha", and the standard `blendFunc(SRC_ALPHA, ONE_MINUS_SRC_ALPHA)` "is wrong if your result is transparent"; correct options are `blendFuncSeparate(SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ONE, ONE_MINUS_SRC_ALPHA)` for straight-alpha sources or `blendFunc(ONE, ONE_MINUS_SRC_ALPHA)` for premultiplied ones. https://limnu.com/webgl-blending-youre-probably-wrong/
- `UNPACK_PREMULTIPLY_ALPHA_WEBGL` ("Multiplies the alpha channel into the other color channels") and `UNPACK_COLORSPACE_CONVERSION_WEBGL` (`BROWSER_DEFAULT_WEBGL` vs `NONE`) apply to `texImage2D`/`texSubImage2D` unpacking. https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/pixelStorei
- `alpha:false`: MDN best practices warns "Specifying alpha:false during context creation causes the browser to composite the WebGL-rendered canvas as though it were opaque ... on some platforms, this capability unfortunately comes at a significant performance cost" and recommends producing alpha 1.0 yourself instead. webglfundamentals takes the opposite view ("probably the best option" since the backbuffer is RGB only). The two sources disagree; the safe reading is: keep `alpha:true, premultipliedAlpha:true`, render premultiplied, clear to opaque, and only try `alpha:false` as a measured optimization. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices ; https://webglfundamentals.org/webgl/lessons/webgl-and-alpha.html
- MDN also: "RGB8 in particular is often surprisingly slow, as masking out the alpha channel and/or patching blend functions has fairly high overhead. Prefer to use RGBA8 and ignore the alpha yourself." Same page.
- `preserveDrawingBuffer:true` "can cause significant performance loss on some platforms"; reading the canvas after the frame returns without it is undefined. https://registry.khronos.org/webgl/specs/latest/1.0/
- `desynchronized:true` "tells the underlying system to skip as much compositing as it is able"; WebGL canvases then "require preserveDrawingBuffer: true to prevent flicker"; tearing possible on front-buffer platforms; a translucent canvas can be desynchronized only if no DOM elements sit above it. Latency win for input-driven UI, at the cost of the preserveDrawingBuffer penalty; measure before adopting. https://developer.chrome.com/blog/desynchronized

### A.5 Buffer and texture upload cost model

- MDN best practices: prefer `texStorage2D` + `texSubImage2D` over repeated `texImage2D` (with `texImage*` "there is no way the driver can actually prepare the texture in GPU memory until the first time the texture is drawn"); DOM-element uploads "will incur a processing pass that will temporarily switch GL Programs internally, causing a pipeline flush", so "Prefer doing uploads before starting drawing, or at least between pipelines"; skip mipmaps for UI textures (`TEXTURE_MIN_FILTER = LINEAR`, saves "the 30% memory surcharge"); avoid `getError`, `getParameter`, `readPixels`, `checkFramebufferStatus` on hot paths ("Even basic requests can take as long as 1ms"); "If you have 1000 sprites to paint, try to do it as a single drawArrays() or drawElements() call." https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices
- Orphaning does not work as on desktop: Ken Russell, "bufferData(target, size, usage) call is guaranteed to initialize the buffer to 0, so it can't be a no-op", and "I would recommend just keeping your code simple and not doing the bufferData(...) call attempting to abandon the buffer"; instead "keeping around two buffers of the same size and alternating which one you draw with and which one you populate". Chrome "replaces it with a call to glBufferData depending on whether, per-platform, glBufferData or glBufferSubData were measured as being faster." https://groups.google.com/g/webgl-dev-list/c/vMNXSNRAg8M
- WebGL validates index buffers on the CPU: Firefox "validate[s] at draw call time, with a (pretty naive) cache" and invalidates on upload; users report 100 ms pauses from `bufferSubData` into huge buffers. Keep per-frame dynamic buffers small and separate from static ones. https://groups.google.com/g/webgl-dev-list/c/8gfFD7eTUYQ
- UBO strategy that works on ANGLE: one large per-frame UBO written once with `bufferSubData`, draws pick ranges with `bindBufferRange` (Andre Weissflog); Corentin Wallez: on D3D11 "ConstantBufferOffsetting" needs D3D11.1, older systems get emulation with extra copies per draw; Jamie Madill: "buffer offsetting works well on Windows 8 and 10 machines"; Intel had "some issues with how ANGLE does caching"; double-buffer the UBO per frame to avoid sync stalls; alignment of 256 bytes wastes space for small per-draw blocks. https://groups.google.com/g/webgl-dev-list/c/-Wt6WF9vS4o

### A.6 ANGLE on Windows (D3D11 translation) gotchas

- ANGLE "is the default WebGL backend for both Google Chrome and Mozilla Firefox on Windows platforms" and "Chrome uses ANGLE for all graphics rendering on Windows, including the accelerated Canvas2D implementation"; backends: D3D11 (Windows), Metal (macOS 10.14+), Vulkan/GLES (Android/Linux). Electron inherits this. https://chromium.googlesource.com/angle/angle/+/HEAD/README.md
- Texture uploads on ANGLE/D3D11: ANGLE creates a staging texture of the same dimensions, maps and fills it, then `CopySubresourceRegion`; "filling works best when the rows are aligned to 256 bytes"; "redefining the texture contents (even with exactly the same values) forces it to recreate both staging and device local textures"; D3D11 has no buffer-to-texture copy so PBO upload paths are not used (kvark, WebRender issue). Rule: allocate atlases once with `texStorage2D`, update with `texSubImage2D`, never re-`texImage2D` a live texture. https://github.com/servo/webrender/issues/2960
- Uniform updates: per-draw `uniform*` calls on D3D11 dirty a constant buffer that ANGLE re-uploads; the angleproject thread shows uniform upload (`D3D11...` calls inside uniform buffer update) dominating a profile, and advises UBOs; in that specific case the extra cost came from D3D debug layers being enabled, which browsers do not do. Treat individual uniforms as per-draw cost and move per-frame state into a UBO. https://groups.google.com/g/angleproject/c/OLe_yOx7ecU
- Spec-level D3D-motivated restrictions (index vs data buffers, primitive restart always on, no swizzle, transform feedback double binding) are listed in A.1.
- Sync points that stall the renderer process: `getError`, `getParameter`, `checkFramebufferStatus`, `readPixels` to CPU ("finish + round-trip"), `getBufferSubData`, `finish`. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices ; https://registry.khronos.org/webgl/specs/latest/2.0/#webgl_gl_differences

### A.7 Typical limits (Web3D Survey, WebGL2 reports)

- `MAX_TEXTURE_SIZE`: 4096 in 100% of reports, 16384 in 84%, 32768 in 1%; Firefox reports start at 2048 for 100%, 4096 for 99%. https://web3dsurvey.com/webgl2/parameters/MAX_TEXTURE_SIZE
- `MAX_TEXTURE_IMAGE_UNITS`: 16 in 100%, 24 in 14%, 64 in 1%. https://web3dsurvey.com/webgl2/parameters/MAX_TEXTURE_IMAGE_UNITS
- `MAX_SAMPLES`: 4 (100%), 8 (62%), 16 (20%). https://web3dsurvey.com/webgl2/parameters/MAX_SAMPLES
- MDN's cross-system minimums: `MAX_TEXTURE_SIZE 4096`, `MAX_TEXTURE_IMAGE_UNITS 8` (WebGL1; WebGL2 requires 16), `MAX_VERTEX_ATTRIBS 16`, `MAX_VARYING_VECTORS 8`. "Your desktop may support 16k textures ... but most other systems don't". https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices ; https://webgl2fundamentals.org/webgl/lessons/webgl-texture-units.html
- Design consequence: atlases at 4096x4096 (RGBA8 = 64 MB) are the safe ceiling; 8192 is safe on desktop; use a `TEXTURE_2D_ARRAY` of 2048 or 4096 pages to grow.

### A.8 Electron specifics

- GPU process and flags: `app.disableHardwareAcceleration()` "can only be called before app is ready"; `app.getGPUFeatureStatus()` returns the chrome://gpu feature table (after `gpu-info-update`); `app.getGPUInfo('basic'|'complete')`; "By default, Chromium disables 3D APIs (e.g. WebGL) until restart on a per domain basis if the GPU process crashes too frequently", override with `app.disableDomainBlockingFor3DAPIs()`; GPU crashes surface as `child-process-gone` with reasons like `crashed`, `oom`, `killed`. https://www.electronjs.org/docs/latest/api/app
- Chromium switches are appended with `app.commandLine.appendSwitch()` before `ready`; Electron documents only `--force_high_performance_gpu` / `--force_low_power_gpu` and defers to Chromium's flag list for the rest. https://www.electronjs.org/docs/latest/api/command-line-switches
- SwiftShader: "automatic fallback to WebGL backed by SwiftShader has been deprecated" (shipped in Chrome 137 per the Intent to Remove); headless/CI must pass `--use-gl=angle --use-angle=swiftshader-webgl --enable-unsafe-swiftshader` (or `--use-angle=swiftshader` for the GLES driver path); "SwiftShader is a high security risk due to JIT-ed code running in Chromium's GPU process". - Screenshots: `contents.capturePage(rect, {stayHidden, stayAwake})` returns `Promise<NativeImage>`; a hidden window is "considered visible when its browser window is hidden and the capturer count is non-zero". https://www.electronjs.org/docs/latest/api/web-contents

- `OffscreenCanvas` + `transferControlToOffscreen()` lets the renderer run WebGL in a Worker with `requestAnimationFrame` available in the worker (Baseline March 2023). Useful for isolating UI rendering from main-thread JS in both Electron and browser builds. https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas

### A.9 WebGPU as a future backend: the abstraction boundary that keeps WebGL2 code portable

- WebGPU differences (Chrome doc): "WebGL has a lot of global state ... A pipeline is immutable"; "WebGPU is designed to be completely asynchronous. The error model and all other operations happen asynchronously"; WGSL instead of GLSL; "buffers and textures are immutable" (no resizing/reformatting); readback is async only; compute is WebGPU-only. https://developer.chrome.com/docs/web-platform/webgpu/from-webgl-to-webgpu
- Figma's port (C++/WASM, same shaders): they first changed their WebGL layer so draw calls take everything explicitly, `context->draw(vertexBuffer, framebuffer, {texture}, material, ...)`, which "fixed a handful of bugs in our WebGL renderer before we even touched WebGPU"; they then introduced `encodeDraw(uniformStructData, material, ...)` + `submit()` so uniform allocation and upload are batched per frame instead of per draw; GLSL is translated to WGSL with naga; "WebGL supports synchronous pixel readback, but in WebGPU it's only possible to read back data from the GPU asynchronously"; they fall back to WebGL mid-session on device loss; planned WebGPU-only wins are compute blur, MSAA, RenderBundles. https://www.figma.com/blog/figma-rendering-powered-by-webgpu/
- PixiJS v8 was rebuilt with WebGPU "as a core paradigm" with WebGL parity; the three-step pipeline (build instructions, upload all scene data once, execute) is backend-neutral. https://pixijs.com/blog/pixi-v8-launches ; https://pixijs.com/blog/pixi-v8-beta
- Boundary rules that follow: (1) render passes are explicit objects with attachments + clear ops, never implicit framebuffer binds; (2) per-draw state is an immutable "pipeline key" (shader variant, blend, depth/stencil, vertex layout, cull) that the WebGL backend maps to state caching; (3) resources are grouped into bind groups (UBO ranges + texture/sampler sets) resolved to `bindBufferRange` + texture units on WebGL; (4) uniforms live only in UBOs (WebGPU has no `uniform1f`); (5) buffers/textures are allocated once at fixed size (`texStorage2D`, `bufferData(size)`), updated with sub-updates; (6) all readback is async via fences; (7) no `getError`/`getParameter` on hot paths (WebGPU has no synchronous errors); (8) shader source authored in GLSL ES 3.00 with a mechanical translation path (naga/Tint) in mind: no dynamic sampler indexing, uniforms in `std140` blocks, one `out vec4` per attachment.

## B. Prior art (JS/TS and other 2D/UI renderers)

### B.1 PixiJS v8

- Pipeline: "Traverse the scene graph and construct a set of instructions. Upload all scene data to GPU in one go. Execute rendering based on the instructions." Instruction reuse: "If the scene graph remains unchanged in subsequent frames, we reuse the existing rendering instructions"; "If no elements in the scene change position, the data upload step is entirely skipped." Reported 100k static sprites: 21 ms to 0.12 ms CPU. https://pixijs.com/blog/pixi-v8-beta ; https://pixijs.com/blog/pixi-v8-launches
- Render groups: "Render Groups are essentially containers that PixiJS treats as self-contained scene graphs"; transforms, tint, alpha "offloaded to the GPU"; each group "prepare[s] a set of render instructions specifically for the group"; the root is always a render group; "using too many can actually degrade performance". `isRenderGroup` = "rendered as a separate pass, with its own set of instructions". https://pixijs.com/8.x/guides/concepts/render-groups ; https://pixijs.download/release/docs/scene.Container.html
- Ordering: children render in insertion order; `zIndex` "A higher value will mean it will be moved towards the front of the rendering order", scoped to the parent; `sortableChildren` sorts "when the next render is called, or manually if sortChildren() is called"; `sortChildren()` "Only sorts if container is marked as dirty"; `alpha` is "relative to its parent's opacity" (per-object multiplication, not group opacity). https://pixijs.download/release/docs/scene.Container.html
- RenderLayers (v8.6+): "allow control of the draw order independently of the logical hierarchy"; objects "maintain transformations ... from their logical parent, even when attached to RenderLayers"; a layer's own position among its siblings decides when it draws; `layer.sortableChildren` + `sortRenderLayerChildren()` sort by zIndex within the layer; manual reattachment after removal. https://pixijs.com/8.x/guides/concepts/render-layers
- Masks: "Axis-aligned Rectangle masks are the fastest (as they use scissor rect)", "Graphics masks are second fastest (as they use the stencil buffer)", "Sprite masks are the third fastest (they use filters). They are really expensive"; "100s of masks will really slow things down"; sprite masks read the red channel unless `setMask({channel:'alpha'})`. https://pixijs.com/8.x/guides/concepts/performance-tips ; https://pixijs.download/release/docs/scene.Container.html
- Batching: DefaultBatcher vertex = "x, y, u, v, color, textureIdAndRound -> total = 6" floats (24 bytes); batches keyed on "tints, roundPixels, texture, transform"; `break()` "when a batch gets too big, or we need to switch to a different type of rendering" (filters, masks); blend mode changes split batches ("ScreenSprite / NormalSprite / ScreenSprite / NormalSprite would be 4 draw calls"); up to 16 textures per batch via a sampler array + constant-index switch. https://pixijs.download/release/docs/rendering.DefaultBatcher.html ; https://pixijs.com/8.x/guides/concepts/performance-tips
- Text: `Text` (canvas-rasterized, "Avoid when: You're changing text every frame"), `BitmapText` (atlas, "Ideal for thousands of changing labels", fonts generated on the fly), `HTMLText` (emoji, RTL, slowest). https://pixijs.com/8.x/guides/components/scene-objects/text
- Relevance: PixiJS keeps painter's order by default and pays for z-order with explicit per-container sorting; group effects (filters, sprite masks) are done by breaking the batch and rendering to an intermediate texture. Its "instructions list + reuse when unchanged" is the retained-over-immediate model the spec wants.

### B.2 Phaser 3/4

- Display list: "By default, Game Objects are rendered in the order in which they were added to the Display List"; `setDepth` "allows you to change the rendering order of Game Objects, without actually moving their position in the display list"; depth changes queue a depth sort in the scene; `bringToTop/sendToBack/moveUp/moveDown`. Only `Container` has children. https://docs.phaser.io/phaser/concepts/gameobjects/display-list ; https://docs.phaser.io/api-documentation/namespace/gameobjects-components-depth
- Masks (Phaser 3): GeometryMask "Renders the Geometry Mask's underlying Graphics object to the OpenGL stencil buffer and enables the stencil test", nests via INCR/DECR ("Is this an INCR stencil or a DECR stencil?"), `invertAlpha`, and post-render "Flushes all rendered pixels and disables the stencil test". BitmapMask is render-to-texture, WebGL only. In the current docs GeometryMask is canvas-only and WebGL masking moved to the Filters system (`FilterList#addMask`). https://photonstorm.github.io/phaser3-docs/Phaser.Display.Masks.GeometryMask.html ; https://docs.phaser.io/api-documentation/class/display-masks-geometrymask
- Relevance: flat list + numeric depth + stable sort is the simplest workable ordering model; every mask flushes the batch.

### B.3 Skia / CanvasKit

- `SkCanvas` "maintains a stack of matrices and clips"; `saveLayer` "Saves SkMatrix and clip, and allocates a SkSurface for subsequent drawing", and `restore()` "blends SkSurface with alpha opacity onto the prior layer"; `saveLayerAlpha` is the group-opacity primitive; clip ops `clipRect/clipRRect/clipPath` replace the clip "with the intersection or difference of clip and rect, with an aliased or anti-aliased clip edge"; "There is a layer per call to saveLayer()". https://api.skia.org/classSkCanvas.html ; https://skia.org/docs/user/api/skcanvas_overview/
- GPU AA: for "simple primitives like circles or round-rects, there are shaders that inflate the bounds by a pixel, then use the fragment position to compute the exact distance to the edge of the shape"; paths use MSAA, coverage skirts, or CCPR (Brian Osman). https://groups.google.com/g/skia-discuss/c/OUzwQqxsCmo
- Text gamma: Skia applies a "gamma hack" at glyph-mask creation guessing the destination, plus a "contrast hack" that over-covers thin stems; "black on white text tends to (correctly) get really anemic looking at small sizes" under true linear blending. https://skia.org/docs/dev/design/raster_tragedy/
- CanvasKit: "Skia now offers a WebAssembly build", "Encapsulates a WebGL context as an SkSurface, allowing for direct drawing to an HTML canvas", paragraph shaping included. https://skia.org/docs/user/modules/canvaskit/
- Relevance: the canonical clip-stack + saveLayer semantics; group opacity is an offscreen layer, everything else is painter's order.

### B.4 Flutter (framework layer tree, Impeller)

- Pipeline: build, layout ("passes down size constraints ... Children respond by passing up a size"), paint, composite (`SceneBuilder`), rasterize; layer tree handed to the engine. https://docs.flutter.dev/resources/architectural-overview
- `OpacityLayer` multiplies "The amount to multiply into the alpha channel" over its subtree as a composited layer; "Try to avoid an OpacityLayer with no children"; `debugDisableOpacityLayers` for profiling. https://api.flutter.dev/flutter/rendering/OpacityLayer-class.html
- `Opacity` widget: "For values of opacity other than 0.0 and 1.0, this class is relatively expensive because it requires painting the child into an intermediate buffer"; "If only a single Image or Color needs to be composited with an opacity between 0.0 and 1.0, it's much faster to directly use them without Opacity widgets." https://api.flutter.dev/flutter/widgets/Opacity-class.html
- Impeller: "All shader compilation and reflection is performed offline at build time"; layers Renderer / Entity ("provides a framework for building 2D renderers") / Display List; text: "Impeller does not do any text layout or shaping, it does render shaped glyph runs" from a glyph atlas. https://github.com/flutter/flutter/blob/main/engine/src/flutter/impeller/README.md
- Impeller clipping uses the stencil buffer with an integer `clip_depth` per entity, and the 2023 depth/stencil arc moves clipping to the depth buffer and introduces stencil-then-cover for complex paths ("We should never use StC with convex shapes"). https://github.com/flutter/flutter/issues/137714 ; https://api.flutter.dev/impeller/classimpeller_1_1_entity.html
- Relevance: group opacity and clips are explicit layer nodes; clip nesting depth is an integer counter that maps to stencil/depth values.

### B.5 Figma

- 2015: "we implemented everything from scratch using WebGL"; "The 2D canvas API is an immediate mode API instead of a retained mode API so all geometry has to be re-uploaded to the graphics card every frame"; the renderer is "a highly-optimized tile-based engine with support for masking, blurring, dithered gradients, blend modes, nested layer opacity, and more" with everything GPU-rendered and anti-aliased. https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/

### B.6 Yoga and JS ports

### B.7 react-native-skia

- `Group` has no opacity prop; "Using the layer property will create a bitmap drawing of the children. ### B.8 Dear ImGui and egui

- ImGui: `ImDrawCmd` carries a per-command `ClipRect` ("Clipping rectangle (x1, y1, x2, y2)"), `TexRef`, `VtxOffset`, `IdxOffset`, `ElemCount`; "The ClipRect/TexRef/VtxOffset fields must be contiguous as we memcmp() them together" (a command is split only when one of these changes); `ImDrawVert` is "pos + uv + col = 20 bytes"; `ImDrawListSplitter` is a "Helper to split a draw list into different layers which can be drawn into out of order, then flattened back", "used by the Columns/Tables API, so items of each column can be batched together in a same draw call". https://github.com/ocornut/imgui/blob/master/imgui.h
- Window order: "Childs are always drawn after parents, in the same order as BeginChild() was called"; explicit z-order is not exposed ("If we expose absolute and arbitrary Z values it means the program needs to allocate/know its Z values for the whole application"); community workaround is stable-sorting windows by an order value before `Render()`, or `BringWindowToDisplayFront`. https://github.com/ocornut/imgui/issues/1328
- egui: layer `Order` enum Background, Middle ("Normal moveable windows that you reorder by click"), Foreground ("Popups, menus etc"), Tooltip, Debug ("always painted last / on top"); meshes are tessellated triangles with a clip rect each; immediate-mode layout disadvantage: "to know the size of the window, we must do the layout, but the layout code also checks for interaction", so sizes are stored and used next frame ("frame-delay for the correct layout"). https://docs.rs/egui/latest/egui/layers/enum.Order.html ; https://github.com/emilk/egui/blob/main/README.md
- Relevance: a small fixed set of named layers plus submission order covers nearly all UI z-ordering needs; per-command clip rects are the batching-friendly clip.

### B.9 Unity (UGUI and UI Toolkit)

- UGUI: "UI elements in the Canvas are drawn in the same order they appear in the Hierarchy. The first child is drawn first, the second child next"; reorder with `SetSiblingIndex` etc. https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/UICanvas.html
- UGUI batching: "Batches are built by walking the hierarchy top-to-bottom and collecting all objects which use the same material, the same texture and do not have intermediate layers"; an intermediate layer is "a graphical object with a different material, whose bounding box overlaps two otherwise-batchable objects and is placed in the hierarchy between the two batchable objects"; "the cost of sorting and analyzing the elements grows more-than-linearly to the number of drawable UI elements on the Canvas"; any change re-runs batch building for the whole Canvas, hence split static vs dynamic canvases and keep "the same Z value, materials, and textures". https://learn.unity.com/course/doozyui-related-tutorials/tutorial/optimizing-unity-ui ; https://unity.com/how-to/unity-ui-optimization-tips
- UI Toolkit draw order: "UI Toolkit draws child elements in the order of the sibling list" (depth-first), no z-index; reorder with `BringToFront`, `SendToBack`, `PlaceBehind`, `PlaceInFront`. https://docs.unity3d.com/6000.2/Documentation/Manual/UIE-draw-order.html
- UI Toolkit renderer: one pre-allocated vertex buffer per panel acting as a heap ("If the UI exceeds the capacity of the vertex buffer, additional buffers are created. This can fragment batching"); uber shader with 8 textures per batch; "Rounded corners and other complex shapes require stencil buffer operations, potentially breaking batches at each masking level"; `DynamicTransform` and `GroupTransform` usage hints move transforms to the GPU; animate transforms not layout properties; `display: none` instead of `opacity: 0`. https://docs.unity3d.com/6000.4/Documentation/Manual/best-practice-guides/ui-toolkit-for-advanced-unity-developers/optimizing-performance.html
- Unity 2D sorting priority (for comparison): Sorting Layer and Order in Layer, then render queue, then distance, then Sorting Group, then material. https://docs.unity3d.com/6000.2/Documentation/Manual/2d-renderer-sorting.html

### B.10 Godot CanvasItem

- "Canvas items are drawn in tree order on their canvas layer. By default, children are on top of their parents"; `z_index` "A node with a higher Z index will display in front of others"; `z_as_relative` (default true): "If this node's Z index is 2 and its parent's effective Z index is 3, then this node's effective Z index will be 2 + 3 = 5"; range `CANVAS_ITEM_Z_MIN` to `CANVAS_ITEM_Z_MAX` (-4096..4096); `y_sort_enabled`; `clip_children` modes. https://docs.godotengine.org/en/stable/classes/class_canvasitem.html ; https://github.com/godotengine/godot-docs/issues/1453
- CanvasLayer: "Layers with a greater number will be drawn above those with a smaller number." https://docs.godotengine.org/en/stable/tutorials/2d/canvas_layers.html
- Known wart: "Clip Children feature only works on child nodes that have the same Z-index as the parent" (z-order and clipping interact badly when clip is a per-z-bucket state). https://github.com/godotengine/godot/issues/75503
- Batching: "batches must share a texture, material, blend mode, shader, and skeleton" and "batching cannot extend across scene layers and Z indices"; the 4.x RD renderer batching PR took a tile-map case from ">573440" draw calls to 36. https://godotengine.org/article/gles2-renderer-optimization-2d-batching/ ; https://github.com/godotengine/godot/pull/92797

### B.11 Rive Renderer

- "the Rive Renderer is a novel geometric reduction of antialiased vector paths into unique triangle patches"; "Fractional coverage for antialiasing is interpolated across triangles and accumulated in pixel local storage. Clockwise triangles get positive coverage, counterclockwise get negative"; incremental blending "no 'cover' step"; backends by capability: pixel local storage (Apple, modern mobile), fragment shader interlock (NVIDIA/Intel), R/W texture fallback, and "MSAA path on truly minimal drivers"; WebGL2 via Emscripten picks "the WebGL-compatible PLS implementation automatically". Feathering extends the one-pixel AA ramp to any width with a gaussian profile. https://rive.app/blog/rive-renderer-now-open-source-and-available-on-all-platforms ; https://rive.app/docs/runtimes/cpp/renderers ; https://rive.app/blog/how-rive-reinvented-feathering-for-the-vectorian-era
- Relevance: shows what analytic coverage AA costs when you go beyond SDF-friendly shapes; for rounded rects, circles, lines, and text an SDF uber-shader is enough.

### B.12 Zed GPUI

- Primitives: "shadows, quads, paths, underlines, and sprites"; original design drew each primitive type in a fixed order so "a rectangle could never be rendered on top of a glyph"; elements "push a Layer to the scene" for stacking contexts; text shaped by the OS (CoreText), glyphs rasterized to alpha and packed in an atlas; instanced draws with per-instance quads. https://zed.dev/blog/videogame
- Current `scene.rs`: every primitive carries `order: DrawOrder` (u32) and `content_mask: ContentMask` (an axis-aligned clip rect); `finish()` sorts each primitive list by `order`; `BatchIterator` merges the per-kind lists by lowest `order`, grouping consecutive same-kind items (and same `texture_id` for sprites) into `PrimitiveBatch::{Shadows, Quads, Paths, Underlines, MonochromeSprites{texture_id}, SubpixelSprites, PolychromeSprites, Surfaces}`. Quad instance = `order, border_style, bounds, content_mask, background, border_color (Hsla), corner_radii (Corners), border_widths (Edges)`; Shadow = `order, blur_radius, bounds, corner_radii, content_mask, color`. https://github.com/zed-industries/zed/blob/main/crates/gpui/src/scene.rs
- Shaders (WGSL, also Metal/HLSL): per-corner radius picked by quadrant; SDF `length(max(vec2(0), p)) + min(0, max(p.x, p.y)) - r`; per-side border widths via `select(...)` per quadrant, inner edge as a quarter-ellipse SDF when widths differ; AA `saturate(0.5 - sdf)`; border color composited over background then `mix(background, blended_border, saturate(0.5 - inner_sdf))`; clip via `distance_from_clip_rect` producing four distances and `if (any(clip_distances < 0)) return 0`; shadow via `erf` polynomial and `blur_along_x` (Evan Wallace's method). https://github.com/zed-industries/zed/blob/main/crates/gpui_wgpu/src/shaders.wgsl (also `crates/gpui_apple/src/shaders.metal`, `crates/gpui_windows/src/shaders.hlsl`)
- Relevance: the closest published design to what the spec needs: one u32 draw order, per-primitive clip rect, kind-merged batches that respect order, SDF quads with per-corner radii and per-side borders, erf shadows.

### B.13 Makepad

- "Makepad is really just a bunch of instanced-array drawcalls on indexed triangles"; "Clipping is done using vertex-shader clipping, so there is no stencil-state"; shaders authored in a Rust DSL (MPSL) that targets GLSL/HLSL/Metal; "retained-geometry, immediate-event" model. https://github.com/makepaddev/makepad-1 ; https://makepad.rs/guide/start/makepad-framework-architecture ; https://lib.rs/crates/makepad

### B.14 WebRender (Servo/Firefox)

- Display list "tells us what we need to draw without being specific to any graphics API"; "First, we do the opaque pass. We go front to back and render all of the opaque shapes. We skip any pixels that are behind others. Then, we do the translucent shapes. These are rendered back to front."; batching is by shader ("there's a border shader, and a text shader, and an image shader"); a render task tree schedules intermediate targets for opacity/filters; glyphs are CPU-rasterized into a GPU texture cache. https://hacks.mozilla.org/2017/10/the-whole-web-at-maximum-fps-how-webrender-gets-rid-of-jank/
- Batching detail: "opaque elements can be drawn in any order without affecting correctness!" thanks to the z-buffer; for blended primitives "WebRender simply iterates over the last 10 blended primitives to see if there is a suitable batch with no other type of primitive overlapping in between." https://mozillagfx.wordpress.com/2018/11/21/webrender-batching/
- Segments: primitives are split so that "segments within the primitive that are (a) opaque (b) have no local clips" go to the opaque pass, e.g. "a segment for each rounded corner, and inner segments". https://github.com/servo/webrender/wiki/Improved-clipping
- Clip chains: "Every display list item has an assigned ClipChain which specifies what ClipNodes are applied to that item"; a clip node has "a clip rectangle along with an optional collection of rounded clip rectangles and a mask image", with an outer and inner rectangle so WebRender "tries to eliminate clips that will not affect rendering"; a clip's spatial node "is completely independent of the SpatialNode applied to the item itself". https://github.com/servo/webrender/blob/master/webrender/doc/CLIPPING_AND_POSITIONING.md
- Picture caching: tiles (2048x512, or 128x128 for UI slices) track dependencies on "primitives, clips, image keys, opacity bindings, transforms"; invalidation produces a per-tile dirty rect "which defines the scissor rect used when replaying the tile's drawing commands". https://doc.servo.org/webrender/picture/index.html
- Nical's GUI-on-GPU notes: "In 2D it tends to be the opposite: lots of content with alpha blending ... which need to be drawn in a specific order"; batch keys hold "shader ID, blend parameters, and texture/buffer IDs"; "If we need more than 100 draw calls this probably going to stutter on some mobile device or low end intel GPU"; axis-aligned clips are done by moving vertices in the vertex shader; "applying a clip to a group of primitive is not equivalent to applying the clip to each primitive in the group individually" under non-supersampling AA; WebRender packs instance data into an `ivec4` of IDs and fetches the rest from buffers/textures; "To be competitive as an app rendering framework, compositing and invalidation are pretty much mandatory"; match caching to workload ("game UIs may not" need heavy pixel caching). https://nical.github.io/drafts/gui-gpu-notes.html

### B.15 The CSS stacking-context model as an ordering model

- "Stacking context is a three-dimensional conceptualization of HTML elements along an imaginary z-axis"; created by the root, positioned + z-index, flex/grid items with z-index, `opacity < 1`, `mix-blend-mode`, `transform`/`filter`/`clip-path`/`mask`, `isolation: isolate`, `will-change`, top layer; "the z-index values of its child stacking contexts only have meaning within its parent's stacking context"; "Stacking contexts are treated atomically as a single unit in the parent stacking context." https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Stacking_context
- CSS 2.1 Appendix E paint order within a stacking context: (1) background and borders of the element, (2) child stacking contexts with negative z-index "in z-index order (most negative first)", (3) in-flow block backgrounds, (4) floats, (5) inline content, (6) positioned descendants with `z-index: auto` or `0` "in tree order", (7) child stacking contexts with positive z-index "(smallest first)", outlines last. https://www.w3.org/TR/CSS21/zindex.html
- Why it matters: opacity < 1 forcing a stacking context is exactly "group opacity needs an isolated group" (see C.3). The rule set gives a well-tested answer to "what does z-index mean inside a scroll view / popup / disabled panel" without global z values (the problem ocornut declined to solve).

### B.16 Sort keys in engines (for the batching key design)

- bgfx: 64-bit sort key with the view id in the highest bits; modes `[view | draw | type=0 | blend | alphaRef | program | depth]` (default, groups by program), depth sort, and sequential `[view | draw | type=2 | sequence | ...]` which "preserves submission order for UI rendering"; `setViewMode` per view. https://bkaradzic.github.io/bgfx/internals.html
- Christer Ericson: key categories from MSB: fullscreen layer, viewport, viewport layer, translucency type, command bit, depth, material; "for opaque geometry we want to reduce state settings", for translucent "sort on depth before material". https://realtimecollisiondetection.net/blog/?p=86
- LinaVG (2D vector UI): per-draw-order buckets, inside a bucket shadows, then shapes, then outlines, then AA borders; "Shapes with different draw orders can not be batched into a single draw call, so usually introducing a new draw order to the system will mean at least 1 additional draw call." https://github.com/inanevin/LinaVG/wiki/10-Draw-Order

## C. Techniques

### C.1 Single-quad SDF rounded rectangle with border and AA

- Inigo Quilez, per-corner radii (`r` = (top-right, bottom-right, top-left, bottom-left) in his convention):

```glsl
float sdRoundedBox( in vec2 p, in vec2 b, in vec4 r ) {
  r.xy = (p.x>0.0)?r.xy : r.zw;
  r.x  = (p.y>0.0)?r.x  : r.y;
  vec2 q = abs(p)-b+r.x;
  return min(max(q.x,q.y),0.0) + length(max(q,0.0)) - r.x;
}
float sdCircle( vec2 p, float r ) { return length(p) - r; }
float sdSegment( in vec2 p, in vec2 a, in vec2 b ) {
  vec2 pa = p-a, ba = b-a;
  float h = clamp( dot(pa,ba)/dot(ba,ba), 0.0, 1.0 );
  return length( pa - ba*h );
}
```
Outlines: "taking their absolute value and then subtracting a constant from their field", i.e. `abs(d) - t` gives a centered stroke of width 2t. https://iquilezles.org/articles/distfunctions2d/

- Border placement from one SDF `d` (negative inside):
  - outside border of width w: fill where `0 <= d <= w` (grow the quad by w);
  - inside border: fill where `-w <= d <= 0`;
  - center: `abs(d) <= w/2`.
  GPUI does inside borders with per-side widths by computing a second SDF for the inset rect (quarter-ellipse corners when widths differ) and mixing border over background by `saturate(0.5 - inner_sdf)`. https://github.com/zed-industries/zed/blob/main/crates/gpui_wgpu/src/shaders.wgsl
- AA: coverage = `saturate(0.5 - d)` when `d` is in device pixels (GPUI), or `smoothstep`/`clamp` over one pixel of distance using `fwidth(d)`. Caveat from the analytical-AA article: `fwidth` is `|dx| + |dy|`, "which causes diagonal edges to receive excessive blur", so `length(vec2(dFdx(d), dFdy(d)))` is more accurate, and for UI where the quad is axis-aligned in device pixels you can skip derivatives entirely and use a known pixel size. Both articles note the setup needs `premultipliedAlpha: true` output. https://blog.frost.kiwi/analytical-anti-aliasing/ ; https://randygaul.github.io/graphics/2025/03/04/2D-Rendering-SDF-and-Atlases.html ("Simply blur between boundaries over the region of distance near zero. smoothstep works great for this.")
- Skia does the same for rrects/circles: "inflate the bounds by a pixel, then use the fragment position to compute the exact distance to the edge of the shape". https://groups.google.com/g/skia-discuss/c/OUzwQqxsCmo
- Uber-shader packing: Randy Gaul renders triangles, segments, circles, capsules, polygons and sprites in one draw with a `v_type` attribute and "a simple if-else chain", ~144 bytes/vertex, and recommends sorting inside a draw by shape type to limit divergence. https://randygaul.github.io/graphics/2025/03/04/2D-Rendering-SDF-and-Atlases.html

### C.2 Fast approximate rounded-rect drop shadows

- Evan Wallace: the box shadow is separable: a 2D gaussian-blurred box equals the product of two 1D blurred boxes, and the 1D integral is `F(x) = (1 + erf(x / (sigma sqrt(2)))) / 2`; for rounded corners "use the closed-form solution along the first dimension and sampling along the second dimension" with 4 samples; the shadow quad is padded by `3.0 * sigma`. Code:

```glsl
vec2 erf(vec2 x) {
  vec2 s = sign(x), a = abs(x);
  x = 1.0 + (0.278393 + (0.230389 + 0.078108 * (a * a)) * a) * a;
  x *= x;
  return s - s / (x * x);
}
float gaussian(float x, float sigma) {
  const float pi = 3.141592653589793;
  return exp(-(x * x) / (2.0 * sigma * sigma)) / (sqrt(2.0 * pi) * sigma);
}
float roundedBoxShadowX(float x, float y, float sigma, float corner, vec2 halfSize) {
  float delta = min(halfSize.y - corner - abs(y), 0.0);
  float curved = halfSize.x - corner + sqrt(max(0.0, corner * corner - delta * delta));
  vec2 integral = 0.5 + 0.5 * erf((x + vec2(-curved, curved)) * (sqrt(0.5) / sigma));
  return integral.y - integral.x;
}
```
https://madebyevan.com/shaders/fast-rounded-rectangle-shadows/ (GPUI ships the same `erf` and `blur_along_x`: https://github.com/zed-industries/zed/blob/main/crates/gpui_wgpu/src/shaders.wgsl)
- Raph Levien's alternative: SDF of the rounded rect with an adjusted radius `sqrt(r_c^2 + 1.25 r_b^2)`, a 1D blurred-box cross-section, and corrections for large blur; erf approximated by `x / sqrt(1 + x*x)` style rsqrt; "Accuracy is nearly perfect for the original use case - shadows for UI objects". Cheaper (no sampling loop) when shadows are large. https://raphlinus.github.io/graphics/2020/04/21/blurred-rounded-rects.html
- CSS `box-shadow` semantics to mirror: blur radius b corresponds to a gaussian with sigma = b/2 (Levien's post uses this mapping; verify against the CSS Backgrounds spec: https://www.w3.org/TR/css-backgrounds-3/#shadow-blur).
- Ordering: GPUI draws all shadows of an `order` before its quads; LinaVG draws shadows first per draw-order bucket. Shadows are blended primitives that must sit right below their element in painter's order.

### C.3 Group opacity vs per-primitive alpha

- Compositing spec: "A compositing group is rendered by first compositing the elements of the group onto the initial backdrop. The result of this is a single element containing color and alpha information. This element is then composited onto the group backdrop"; in an isolated group "the initial backdrop shall be black and fully transparent"; simple alpha compositing in premultiplied form is `co = Cs x αs + Cb x αb x (1 - αs)`. https://www.w3.org/TR/compositing-1/
- Per-primitive alpha multiplies each child's alpha, so overlapping children double-blend (a 50% panel with a 50% button shows the panel through the button); group opacity renders the subtree into an offscreen target and blends once. CSS makes `opacity < 1` create a stacking context for exactly this reason. https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Stacking_context
- Cost: Flutter, "requires painting the child into an intermediate buffer", and "a render target switch can sometimes cost about 1ms" on older GPUs; Skia `saveLayer` allocates an `SkSurface`; react-native-skia's `layer` prop; WebRender schedules such targets in a render-task tree so independent ones share a pass. https://api.flutter.dev/flutter/widgets/Opacity-class.html ; https://api.skia.org/classSkCanvas.html ; https://hacks.mozilla.org/2017/10/the-whole-web-at-maximum-fps-how-webrender-gets-rid-of-jank/
- Cheap path: when a group has one primitive (or non-overlapping primitives), multiply alpha into the primitives (Flutter's "much faster to directly use them without Opacity widgets"; PixiJS does only this). The spec should make this the default and reserve render-to-texture for `opacity < 1` on groups whose children overlap or use blend modes.

### C.4 Clipping options and batching implications

| Stencil | arbitrary, incl. rounded | integer depth via INCR/DECR (Phaser) or `clip_depth` (Impeller); 8-bit stencil gives 255 levels | mask draw + state changes per level; Unity: "Rounded corners and other complex shapes require stencil buffer operations, potentially breaking batches at each masking level" | https://photonstorm.github.io/phaser3-docs/Phaser.Display.Masks.GeometryMask.html ; https://github.com/flutter/flutter/issues/137714 ; https://docs.unity3d.com/6000.4/Documentation/Manual/best-practice-guides/ui-toolkit-for-advanced-unity-developers/optimizing-performance.html |

| Rounded clip via SDF in shader | rounded rect (one per primitive, or a small fixed number) | not general | none if packed per instance; coverage multiplies the primitive's coverage | GPUI `PolychromeSprite.corner_radii`; WebRender rounded clip segments https://github.com/servo/webrender/wiki/Improved-clipping |

Also: WebRender keeps an outer/inner rect per clip so clips that provably do not touch the item are dropped, and rounded-corner clips are split into corner segments (masked) and inner segments (unmasked, opaque pass). https://github.com/servo/webrender/blob/master/webrender/doc/CLIPPING_AND_POSITIONING.md . ### C.5 Painter's order vs depth buffer with transparency

- The failure: "the depth test does not care if the fragment has transparency or not, so the transparent parts are written to the depth buffer as any other value", so later fragments behind a translucent pixel are discarded; fix is "Draw all opaque objects first. Sort all the transparent objects. Draw all the transparent objects in sorted order" (back to front). https://learnopengl.com/Advanced-OpenGL/Blending
- UI is mostly blended: anti-aliased edges, text, shadows, translucent panels. Nical: "In 2D it tends to be the opposite: lots of content with alpha blending ... which need to be drawn in a specific order". https://nical.github.io/drafts/gui-gpu-notes.html
- When a depth pre-pass helps: WebRender's opaque pass draws front to back with z-write so "opaque elements can be drawn in any order", then an alpha pass back to front; to get pixels into the opaque pass primitives are segmented (opaque interiors vs AA/rounded edges). Payoff is overdraw reduction on big opaque panels and batch freedom; cost is segmentation and a depth attachment. https://mozillagfx.wordpress.com/2018/11/21/webrender-batching/ ; https://github.com/servo/webrender/wiki/Improved-clipping
- For a game UI with a few hundred to a few thousand quads, GPUI/PixiJS/ImGui/egui all skip the depth buffer and rely on sorted submission plus kind/texture batching. bgfx offers the same as its "sequential" view mode. https://bkaradzic.github.io/bgfx/internals.html

### C.6 Text

- SDF vs MSDF: msdfgen, "MSDFs can reproduce sharp corners almost perfectly" using three channels and `median(r,g,b)`; shader: `float sd = median(msd.r, msd.g, msd.b); float screenPxDistance = screenPxRange()*(sd - 0.5); float opacity = clamp(screenPxDistance + 0.5, 0.0, 1.0);`; "interpret the MSDF color channels in linear space just like the alpha channel and not as sRGB"; `screenPxRange()` must stay above ~2 or AA breaks; `-pxrange` controls the encoded distance range. https://github.com/Chlumsky/msdfgen
- msdf-atlas-gen: atlas types hardmask, softmask, sdf, psdf, msdf (default), mtsdf ("a combination of MSDF and true SDF in the alpha channel", useful for outlines/shadows); JSON/CSV/Artery Font layouts with metrics and kerning pairs; `-size`, `-minsize`, `-pxrange` (default 2), bin packing or `-uniformgrid`; charset files. https://github.com/Chlumsky/msdf-atlas-gen (msdf-bmfont-xml produces BMFont-format XML/JSON from the same generator: https://github.com/soimy/msdf-bmfont-xml)
- Canvas-rasterized atlases: PixiJS `Text` rasterizes with the 2D canvas (full CSS font control, emoji via the OS, slow to change), `BitmapText` uses atlases and "BitmapFonts can now be generated on the fly". Canvas rasterization is the practical emoji/color-glyph fallback in a browser: rasterize the emoji run with `fillText` into a polychrome atlas page and draw it as a sprite (GPUI has the same monochrome vs polychrome sprite split). https://pixijs.com/8.x/guides/components/scene-objects/text ; https://pixijs.com/blog/pixi-v8-launches ; https://github.com/zed-industries/zed/blob/main/crates/gpui/src/scene.rs
- Subpixel positioning: "each offset is its own unique rasterization, so you're incredibly unlikely to get cache hits"; snap to quarter pixels (4 variants per glyph); grayscale AA "will degrade gracefully" under transforms, subpixel (LCD) AA "will look terrible" when misaligned and "has become less relevant" on HiDPI. Nical: subpixel positioning is "Essential to avoid kerning artifacts". SDF/MSDF glyphs sidestep the cache problem (one texture, any offset) at the cost of hinting. https://faultlore.com/blah/text-hates-you/ ; https://nical.github.io/drafts/gui-gpu-notes.html
- Gamma: linear blending "tends to make black on white look slightly heavier"/thin depending on encoding; Skia applies a gamma hack and a contrast hack when building glyph masks; FreeType: "Text must be rendered with linear alpha blending and gamma correction" but "Gamma correction essentially lightens fonts ... glyphs ... suddenly thin out", so "Stem darkening should only be enabled when doing gamma correction"; PureDev uses gamma 1.43 rather than 2.2 as the compromise; Vello: a "theoretically 'correct' approach to gamma often yields text and hairline strokes that appear weak and spindly". https://skia.org/docs/dev/design/raster_tragedy/ ; https://freetype.org/freetype2/docs/hinting/text-rendering-general.html ; https://www.puredevsoftware.com/blog/2019/01/22/sub-pixel-gamma-correct-font-rendering/ ; https://github.com/linebender/vello/blob/main/doc/vision.md
- Shaping: "you cannot correctly draw text character-by-character" because "the shape of a character depends on its neighbours"; HarfBuzz handles ligatures ("f, i" to "ﬁ"), mandatory Tamil substitutions, Arabic positional forms ("four different variants"), mark positioning. For a game UI with Latin/Cyrillic/Greek text, kerning pairs from the atlas JSON plus grapheme clusters are acceptable; anything with Arabic/Indic/Thai needs a shaper (HarfBuzz via WASM, or rasterize such runs through canvas 2D). https://faultlore.com/blah/text-hates-you/ ; https://harfbuzz.github.io/why-do-i-need-a-shaping-engine.html
- Measurement and wrapping: canvas `measureText` returns `width`, `actualBoundingBoxLeft/Right/Ascent/Descent`, `fontBoundingBoxAscent/Descent`, baselines (Baseline since 2015); UAX #14 "produces a set of positions called 'break opportunities'" while "The selection of actual line break positions ... is in the domain of higher level software"; `Intl.Segmenter` gives locale-aware grapheme/word/sentence segmentation (Baseline April 2024, handles Japanese without spaces); greedy first-fit is what LibreOffice/Word use, Knuth-Plass "minimizes the sum of the squares of the lengths of the spaces at the end of lines" (TeX); text-hates-you: wrapping and shaping are circular, so "shape text assuming single-line layout, break when space exhausted, repeat". https://developer.mozilla.org/en-US/docs/Web/API/TextMetrics ; https://www.unicode.org/reports/tr14/ ; https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter ; https://en.wikipedia.org/wiki/Line_wrap_and_word_wrap ; https://faultlore.com/blah/text-hates-you/
- Clay's warning applies to any layout engine with a measure callback: "It is essential that this function is as fast as possible", so cache measurements by (font, size, string). https://github.com/nicbarker/clay

### C.7 Pixel snapping and devicePixelRatio

- `devicePixelRatio` = physical pixels per CSS pixel; changes with zoom and monitor moves, observe with `matchMedia('(resolution: Ndppx)')`. https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio
- Canvas size: `Math.round(canvas.clientWidth * dpr)` (rounding function is unspecified), and on Chromium `ResizeObserver` with `{box: 'device-pixel-content-box'}` "gives the correct answer. The other paths are imperfect fallbacks"; Safari zoom breaks the `getBoundingClientRect * dpr` path. https://webglfundamentals.org/webgl/lessons/webgl-resizing-the-canvas.html . MDN: non-integer scaling causes moire; use ResizeObserver device-pixel-content-box. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices
- Half-pixel rule: a 1-unit stroke "extends to half the line width on either side of the path", so odd-width lines at integer coordinates straddle two pixels; offset by 0.5. https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Applying_styles_and_colors
- In GL, `gl_FragCoord.xy` are pixel centers at half-integers (lower-left origin). So for an SDF rect, if you want a 1-device-pixel border to land on whole pixels, snap the rect's device-space edges to integers and the border width to an integer; the SDF then evaluates to exactly ±0.5 at pixel centers on the edge. https://registry.khronos.org/OpenGL-Refpages/es3.0/html/gl_FragCoord.xhtml
- Layout in CSS pixels, snap in device pixels at paint time (round `x*dpr`), never round layout coordinates themselves; PixiJS exposes `roundPixels` per batch item for the same reason. https://pixijs.download/release/docs/rendering.DefaultBatcher.html

### C.8 Batching key design and instanced quads

- Key contents from prior art: shader variant, blend mode, texture(s)/atlas page, render target, clip state if it is GPU state (scissor/stencil), and draw order bucket. Nical: "batch keys" = "shader ID, blend parameters, and texture/buffer IDs"; PixiJS: texture, blend mode, filter/mask; Godot: "texture, material, blend mode, shader, and skeleton" and never across z-indices; Unity: material, texture, no intermediate overlapping layer. https://nical.github.io/drafts/gui-gpu-notes.html ; https://pixijs.com/8.x/guides/concepts/performance-tips ; https://godotengine.org/article/gles2-renderer-optimization-2d-batching/ ; https://learn.unity.com/course/doozyui-related-tutorials/tutorial/optimizing-unity-ui
- Order-preserving merge: GPUI sorts per-kind lists by `order` and merges by lowest order, so a batch only spans consecutive orders of one kind; WebRender looks back through "the last 10 blended primitives" for a compatible batch with no overlapping different-kind primitive in between. https://github.com/zed-industries/zed/blob/main/crates/gpui/src/scene.rs ; https://mozillagfx.wordpress.com/2018/11/21/webrender-batching/
- Instance layout candidates:
  - GPUI Quad: order u32, border_style u32, bounds 4xf32, content_mask 4xf32, background (solid or gradient), border_color 4xf32, corner_radii 4xf32, border_widths 4xf32; well over 100 bytes with gradients.
  - Nical/WebRender: an `ivec4` of IDs (primitive, transform, pattern, mask) per instance, bulk data fetched from a texture/buffer; "Store only offsets" for glyphs.
  - Randy Gaul: ~144 bytes per vertex for an everything-shader.
  - PixiJS: 24 bytes per vertex, 4 vertices per quad (96 bytes per sprite).
  A 64-byte instance for the common case fits in 4 vec4 attributes: `vec4 rect(x,y,w,h)`, `vec4 uv_or_params`, `uvec4 packed(colorRGBA8, borderRGBA8, cornerRadii 4x u8 or 2x u16, flags|kind|texSlot|clipIndex)`, `vec4 border_widths/extra`; clip rects and gradients go in a UBO/texture indexed by `clipIndex`. WebGL2 allows 16 vec4 attributes (256 bytes) but 64 bytes keeps the vertex fetch cheap; use `vertexAttribIPointer` for the packed integer lane. https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/vertexAttribIPointer
- Vertex source: a unit quad with `gl_VertexID` (no vertex buffer) or a 4-vertex VBO, `drawArraysInstanced(TRIANGLE_STRIP, 0, 4, n)`; per-instance attribute divisor 1; Makepad and GPUI both are "instanced-array drawcalls". Nical notes instancing puts each instance in its own wavefront but "we aren't spending that much time in the vertex shader". https://webgl2fundamentals.org/webgl/lessons/webgl-drawing-without-data.html ; https://nical.github.io/drafts/gui-gpu-notes.html
- Multi-texture within a batch: `TEXTURE_2D_ARRAY` pages (one sampler, layer index per instance) or up to 16 samplers with a constant-index switch (GLSL ES 3.00 rule). `WEBGL_multi_draw` only helps when many distinct ranges must be issued (not Firefox).

### C.9 Anti-aliasing without MSAA

- Analytic coverage from an SDF (C.1) for quads, circles, lines, borders; Skia does this for "circles or round-rects"; MSAA is "hardly 'high quality'" and slow on Intel (nical); Rive uses coverage accumulation in pixel local storage; Vello uses exact-area coverage in compute. For arbitrary paths in WebGL2 the options are stencil-then-cover with MSAA renderbuffers (`renderbufferStorageMultisample` + `blitFramebuffer`) or coverage skirts (egui feathering, Skia's "skirt of triangles"). https://groups.google.com/g/skia-discuss/c/OUzwQqxsCmo ; https://nical.github.io/drafts/gui-gpu-notes.html ; https://github.com/linebender/vello/blob/main/doc/vision.md ; https://github.com/emilk/egui/blob/main/README.md
- Pitfalls: coverage must be multiplied into premultiplied color (C.10); `fwidth` over-blurs diagonals; clipping AA primitives per-primitive vs per-group differs (nical); LinaVG draws AA borders last per bucket and notes intersection artifacts. https://blog.frost.kiwi/analytical-anti-aliasing/ ; https://github.com/inanevin/LinaVG/wiki/10-Draw-Order

### C.10 Premultiplied alpha end to end

1. Textures: premultiply at load (`UNPACK_PREMULTIPLY_ALPHA_WEBGL` for DOM images, or offline for atlas PNGs). Reason (NVIDIA): "With traditional post-multiplied alpha, this result will be incorrect" under bilinear filtering and mipmapping; premultiplied storage "preserved the intent of the higher resolution mipmap". https://developer.nvidia.com/content/alpha-blending-pre-or-not-pre ; https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/pixelStorei
2. Shaders: output `vec4(rgb * a, a)`; SDF coverage multiplies the whole premultiplied color; tint multiplies premultiplied color by premultiplied tint. https://limnu.com/webgl-blending-youre-probably-wrong/
3. Blend state: `blendFunc(ONE, ONE_MINUS_SRC_ALPHA)` (normal), `blendFunc(ONE, ONE)` (additive; McDonald notes additive and normal unify under premultiplication), multiply etc. via `blendFuncSeparate`. https://developer.nvidia.com/content/alpha-blending-pre-or-not-pre ; https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/blendFuncSeparate
4. Offscreen layers (group opacity, filters): keep premultiplied; composite the layer with `ONE, ONE_MINUS_SRC_ALPHA` and a constant opacity multiplied into both color and alpha.
5. Canvas: leave `premultipliedAlpha: true` (default); the compositor "will assume the drawing buffer contains colors with pre-multiplied alpha"; `toDataURL` de-multiplies lossily. https://registry.khronos.org/webgl/specs/latest/1.0/
6. MSDF atlases are not color data: sample them with `UNPACK_COLORSPACE_CONVERSION_WEBGL = NONE` and no premultiply (msdfgen: "interpret the MSDF color channels in linear space"). https://github.com/Chlumsky/msdfgen

### C.11 sRGB vs linear for UI

- Physically, blending, blurring, and resizing belong in linear light (Ottosson: "use a linear version of sRGB when doing any sort of blending, blurring, resizing or transparency blending"); but "sRGB and perceptual color spaces blend white and black similarly, while linear blending is much brighter", which is why sRGB-space blends of thin AA edges and gradients look expected to users. https://bottosson.github.io/posts/colorwrong/
- Text is the decisive case: correct linear blending makes "black on white text ... really anemic looking at small sizes" (Skia), so Skia/FreeType/Chrome compensate with gamma/contrast hacks. https://skia.org/docs/dev/design/raster_tragedy/ ; https://freetype.org/freetype2/docs/hinting/text-rendering-general.html
- CSS itself interpolates colors in Oklab by default now (`color-interpolation-method`: "When interpolating <color> values, the interpolation color space defaults to Oklab"), with premultiplied alpha, not linear-light sRGB. https://developer.mozilla.org/en-US/docs/Web/CSS/color-interpolation-method
- Practical rule for a UI renderer: keep 8-bit sRGB-encoded targets and blend in that space (matches Skia default, CSS legacy, every existing UI tool, and the artists' source PNGs), do not enable sRGB decode on UI textures, and reserve linear pipelines (SRGB8_ALPHA8 FBO + sRGB textures) for in-world 3D content that is composited beneath the UI. If a linear path is ever needed, render UI to its own sRGB-space target and composite last. Sources for the WebGL mechanics: https://groups.google.com/g/webgl-dev-list/c/jCIN5lu7wzE ; https://www.redblobgames.com/x/2445-srgb-webgl/

## D. In-browser performance monitoring

### D.1 Timers and their precision

- `performance.now()` "is coarsened based on whether or not the document is cross-origin isolated": 5 µs isolated, 100 µs non-isolated. Isolation needs `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Opener-Policy: same-origin` on the main document; it also unlocks `SharedArrayBuffer` and `performance.measureUserAgentSpecificMemory()`. https://developer.mozilla.org/en-US/docs/Web/API/Performance/now ; https://web.dev/articles/coop-coep
- Browser specifics (hr-time issue #56, 2018): Chrome "100us + 100us jitter", Edge "20us + 20us jitter", Firefox reduced to 20 µs then 1 ms (`privacy.reduceTimerPrecision`; with `resistFingerprinting` 16.667 ms), Safari "1ms, the same precision as Date.now()". https://github.com/w3c/hr-time/issues/56 ; https://bugzilla.mozilla.org/show_bug.cgi?id=1424341 ; https://bugzilla.mozilla.org/show_bug.cgi?id=1440863
- Electron: you control the headers (or use a custom protocol) so cross-origin isolation is achievable; in the browser build it is an ops decision (every embedded cross-origin asset needs CORP/CORS).
- `requestAnimationFrame` timestamp: "the end time of the previous frame's rendering", "each receives the same timestamp" within a frame, "minimal precision of 1 millisecond", callbacks "generally match the display refresh rate" (60/75/120/144 Hz), paused in background tabs; always use the timestamp for animation. https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame

### D.2 PerformanceObserver entry types

- Long Tasks: "any uninterrupted period where the main UI thread is busy for 50ms or longer", `duration` "with a 1ms granularity", `observe({type:'longtask', buffered:true})`; experimental, not Baseline. https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming
- Long Animation Frames (Chrome/Edge 123+): "a rendering update is delayed beyond 50 milliseconds"; entries have `renderStart`, `styleAndLayoutStart`, `blockingDuration` and a `scripts` array with source locations; better than Long Tasks because "a long animation can be made up of any number of tasks". https://developer.chrome.com/docs/web-platform/long-animation-frames
- Event Timing: `processingStart - startTime` (input delay), `processingEnd - processingStart` (handler), `duration` to next paint "rounded to the nearest 8ms", exposed by default at 104 ms, lower with `durationThreshold` (min 16); `interactionId` groups events; basis of INP. https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming

### D.3 Measuring GPU time

- Preferred: `EXT_disjoint_timer_query_webgl2` `TIME_ELAPSED_EXT` around the UI pass; poll `QUERY_RESULT_AVAILABLE` on later frames; discard the frame if `GPU_DISJOINT_EXT` is true; queries cannot nest and only one may be active. Availability per A.2 (Chromium yes, Firefox/Safari off by default). https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/ ; https://github.com/figma/webgl-profiler
- Fallback: `fenceSync(SYNC_GPU_COMMANDS_COMPLETE, 0)` after the frame, `flush()`, then poll `clientWaitSync(sync, 0, 0)` on subsequent frames (`TIMEOUT_EXPIRED` vs `ALREADY_SIGNALED`/`CONDITION_SATISFIED`). This gives "GPU finished frame N at CPU time T" (latency, not GPU busy time) without stalling; `gl.finish()` or a nonzero timeout blocks the thread, and WebGL may clamp the timeout to zero. Chrome reduced `clientWaitSync` precision as a clock. https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/clientWaitSync ; https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices ; https://www.chromium.org/Home/chromium-security/ssca/
- Async readback pattern (for screenshot tests without stalls): `readPixels` into a `PIXEL_PACK_BUFFER`, fence, poll, then `getBufferSubData`. Code is in the MDN best-practices page. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#use_non-blocking_async_data_readback
- WebGPU has `timestamp-query`; stats-gl integrates both paths. https://github.com/RenaudRohlinger/stats-gl

### D.4 Memory

- `performance.measureUserAgentSpecificMemory()`: "includes JavaScript and DOM memory of all iframes, related windows, and web workers in the current process", measured during GC (async), requires cross-origin isolation, Chromium only (89+); it does not report GPU/WebGL allocations. `performance.memory` is the deprecated JS-heap-only predecessor (stats.js's MB panel, needs `--enable-precise-memory-info`). https://web.dev/articles/monitor-total-page-memory-usage ; https://github.com/mrdoob/stats.js
- No WebGL memory query extension exists; track GPU memory yourself by accounting `texStorage`/`bufferData` sizes in the resource layer (the WebGPU boundary in A.9 makes this natural).

Enable "Capture settings > Show custom tracks". console.timeStamp support arrived with Chrome 134's DevTools per the release notes. https://developer.chrome.com/docs/devtools/performance/extension ; https://developer.chrome.com/blog/new-in-devtools-134

### D.7 In-game overlay design (low overhead)

Grounded in the above:
- Sample once per frame: rAF timestamp deltas (frame interval), `performance.now()` around update/layout/build/submit (CPU phases), draw-call/batch/instance/state-change counters from the renderer's command encoder, and the last completed GPU timer query result (one or two frames old). Costs: a handful of `performance.now()` calls (µs each) and counter increments.
- Keep a ring buffer of the last 120 to 600 frames as `Float32Array`s; compute p50/p95/p99 by copying to a scratch array and sorting only when the panel is visible (or every N frames), never per frame.
- Render the overlay through the same UI renderer (a few hundred instanced quads for the graph bars is negligible) rather than a DOM overlay, so it never causes layout or compositor work; toggle with a key.
- Emit `console.timeStamp('ui-frame', t0, t1, 'UI Renderer', 'Game', 'primary')` per frame in dev builds so DevTools traces show the same phases; emit long-frame events (frame delta > 2x refresh interval) as `performance.measure` marks with `detail.devtools` for post-hoc inspection.
- Subscribe to `long-animation-frame` (Chromium) and `event` (durationThreshold 16) observers to attribute hitches to scripts and input handlers; log rather than draw.
- Report GPU timer results only when `GPU_DISJOINT_EXT` was false; show "n/a" on Firefox/Safari.

## E. Layout engines for a game UI

- Full flexbox (Yoga): used by React Native and Unity UI Toolkit ("uses the layout principles of Yoga"); JS via `yoga-layout` (WASM + asm.js, sync import needs top-level await). Unity's guidance: relative (flex) positioning for "permanent, complex UIs", absolute "sparingly for temporary or decorative elements"; "Avoid to use Absolute position mode because it bypasses the built-in layout engine". Costs: measure callbacks on the hot path, WASM boundary crossings, Yoga wins on incremental relayout of large trees. https://www.yogalayout.dev/docs/about-yoga ; https://github.com/facebook/yoga/blob/main/javascript/README.md ; https://docs.unity3d.com/Manual/UIE-LayoutEngine.html ; https://docs.unity3d.com/6000.5/Documentation/Manual/best-practice-guides/ui-toolkit-for-advanced-unity-developers/layouts.html
- Taffy (Rust): "implements the CSS Block, Flexbox and CSS Grid layout algorithms"; powers Servo, Blitz, Bevy, Slint, Lapce/Floem, and "The Zed text editor via the GPUI UI framework"; benchmarks vs Yoga are mixed (Taffy faster on deep trees, Yoga on very wide trees); official WASM bindings "work-in-progress", third-party `taffy-layout` npm provides Flexbox + Grid with measure callbacks. https://github.com/DioxusLabs/taffy ; https://github.com/ByteLandTechnology/taffy-layout
- Pure-JS flexbox: flexily (Yoga-compatible API, "1.5-2.5x" faster initial layout on small trees, "5.5x" faster no-change relayout, 2.5-3.6x smaller, sync init, but slower than Yoga for single-node updates in 400 to 1000 node trees and deep nesting 15+). https://github.com/beorn/flexily
- Clay (C, 4.8k LOC, WASM 15 kB): sizing modes FIT/GROW/FIXED/PERCENT, layout direction, padding, child gap, alignment, floating elements with z-index for tooltips/modals; "outputs a sorted list of rendering primitives"; arena memory, "microsecond layout performance"; text measurement callback "essential that this function is as fast as possible". This is the "small stack/anchor system" done well: two axes, grow/fit, no wrap/grid. https://github.com/nicbarker/clay
- Godot containers: children "give up their own positioning ability", size flags fill/expand/shrink + stretch ratio, `BoxContainer`/`GridContainer`/`MarginContainer`; anchors for "basic multiple resolution handling", containers for "advanced layout". https://docs.godotengine.org/en/stable/tutorials/ui/gui_containers.html
- Flutter: "passes down size constraints ... Children respond by passing up a size", O(n) single pass; layout widgets (Row/Column/Flex/Stack) are built on it. https://docs.flutter.dev/resources/architectural-overview
- egui (immediate): "to know the size of the window, we must do the layout, but the layout code also checks for interaction", so sizes lag a frame and centering needs the stored size; budget "1-2 ms per frame" for full relayout. https://github.com/emilk/egui/blob/main/README.md
- tchayen's TS flexbox: three passes (level-order prep, bottom-up intrinsic sizes for text-wrapping parents, top-down flex resolution and positioning); supports direction, align/justify, `flex`, gap, %/px, absolute/relative, padding/margin; omits wrap, grow/shrink split, grid. https://tchayen.com/how-to-write-a-flexbox-layout-engine
- Trade-off summary: flexbox buys designer familiarity (CSS mental model, UI Builder style tools) and wrapping; a Clay-style fit/grow/fixed/percent system plus anchors covers HUDs, menus, lists, and dialogs with far less code and predictable O(n) cost, and can be extended to `flex-wrap` later. Whichever is chosen, the engine must be measure-callback based (text), dirty-flag incremental (Yoga/flexily numbers show relayout dominates), and must output positions in CSS pixels that the renderer snaps to device pixels.

## F. Recommendations for the spec

### F.1 Design rules (ranked)

1. Painter's order is the contract; z is a sort key, not a depth. Every primitive gets a `(layer, order)` key; sort stably; no depth buffer for UI. Justification: learnopengl (depth + blending fails), nical ("lots of content with alpha blending ... need to be drawn in a specific order"), GPUI (`DrawOrder` u32 sorted per kind), PixiJS/Phaser/ImGui/egui/Unity/Godot all default to submission or tree order. https://learnopengl.com/Advanced-OpenGL/Blending ; https://nical.github.io/drafts/gui-gpu-notes.html ; https://github.com/zed-industries/zed/blob/main/crates/gpui/src/scene.rs
2. Adopt CSS stacking-context semantics for z-index: z-index is local to the nearest stacking context; a node with `zIndex != auto`, `opacity < 1`, a blend mode, a clip with rounded corners, or a render-to-texture effect creates a stacking context and is painted atomically; paint order inside a context follows Appendix E (negative z children, own background/border, normal-flow children in tree order, positive z children). This removes global z bookkeeping (ocornut's objection) while giving popups/tooltips/drag layers predictable behavior; Godot's `z_as_relative` and egui's five named layers are special cases of it. https://www.w3.org/TR/CSS21/zindex.html ; https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Stacking_context ; https://github.com/ocornut/imgui/issues/1328
3. Retained object model that compiles to an immediate command list, and reuses the list when nothing changed. PixiJS v8's "construct instructions, upload once, execute" with "If the scene graph remains unchanged ... we reuse the existing rendering instructions" is the template; nical: retaining drawing parameters is what pays off for game UIs, pixel caching may not. Track dirty flags per subtree (transform, style, layout, order). https://pixijs.com/blog/pixi-v8-beta ; https://nical.github.io/drafts/gui-gpu-notes.html
4. One SDF uber-shader for quads (rounded rect + per-side borders + fills), circles, lines, and shadows, instanced from a unit quad. Per-corner radii via IQ's `sdRoundedBox`; borders inside by default (CSS box model) using a second inset SDF; AA by `saturate(0.5 - d)` in device pixels; shadows via Evan Wallace's erf method with 3 sigma padding. GPUI ships exactly this and Skia uses the same coverage trick for rrects. https://iquilezles.org/articles/distfunctions2d/ ; https://github.com/zed-industries/zed/blob/main/crates/gpui_wgpu/src/shaders.wgsl ; https://madebyevan.com/shaders/fast-rounded-rectangle-shadows/
5. Clip is per-instance data, not GPU state: every primitive carries a pre-intersected axis-aligned clip rect (GPUI `content_mask`, ImGui `ClipRect`, Makepad vertex clipping); rounded-rect clips are one extra SDF per instance; only true masks (arbitrary shapes, nested rounded clips beyond one level) use stencil, and those break the batch explicitly. https://github.com/zed-industries/zed/blob/main/crates/gpui/src/scene.rs ; https://github.com/ocornut/imgui/blob/master/imgui.h ; https://pixijs.com/8.x/guides/concepts/performance-tips
6. Batch key = (render target, shader variant, blend mode, texture set/atlas array, stencil state); merge consecutive same-key primitives in sorted order; allow the WebRender-style lookback (last N primitives, no overlapping different-key primitive in between) as an optimization. Budget: under 100 draw calls per frame (nical's rule of thumb). https://mozillagfx.wordpress.com/2018/11/21/webrender-batching/ ; https://nical.github.io/drafts/gui-gpu-notes.html
7. Group opacity is an explicit layer node (like Flutter `OpacityLayer`/Skia `saveLayer`), rendered to a premultiplied offscreen target and composited once; the optimizer collapses it into per-primitive alpha when the subtree has a single primitive or provably non-overlapping primitives. https://api.flutter.dev/flutter/widgets/Opacity-class.html ; https://api.skia.org/classSkCanvas.html ; https://www.w3.org/TR/compositing-1/
8. Premultiplied alpha everywhere: atlases premultiplied at load, shaders output premultiplied, `blendFunc(ONE, ONE_MINUS_SRC_ALPHA)`, canvas left at `premultipliedAlpha: true`; MSDF pages uploaded without premultiply or colorspace conversion. https://limnu.com/webgl-blending-youre-probably-wrong/ ; https://developer.nvidia.com/content/alpha-blending-pre-or-not-pre ; https://github.com/Chlumsky/msdfgen
9. Blend UI in sRGB-encoded 8-bit space; no sRGB framebuffer, no linear text; keep any linear-light pipeline for 3D content beneath the UI. Skia, FreeType, and Vello all document that linear blending thins text; CSS interpolates in Oklab/sRGB, not linear light. https://skia.org/docs/dev/design/raster_tragedy/ ; https://freetype.org/freetype2/docs/hinting/text-rendering-general.html ; https://developer.mozilla.org/en-US/docs/Web/CSS/color-interpolation-method
10. Text: MSDF atlases (msdf-atlas-gen `mtsdf` for outline/shadow support, pxrange 4 at 32 px), quarter-pixel snapped positions, kerning from the atlas JSON, greedy line breaking on UAX #14 opportunities with `Intl.Segmenter` for graphemes/words, canvas-2D rasterized polychrome sprites for emoji and unsupported scripts, measurement cache keyed by (font, size, string). https://github.com/Chlumsky/msdf-atlas-gen ; https://faultlore.com/blah/text-hates-you/ ; https://www.unicode.org/reports/tr14/ ; https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter
11. Layout in CSS pixels, paint in device pixels: canvas sized via `ResizeObserver` device-pixel-content-box with `Math.round(client * dpr)` fallback; rect edges and 1 px borders snapped to integers at paint time; layout engine is measure-callback based with dirty tracking (flex subset or Clay-style fit/grow/fixed/percent plus anchors, per E). https://webglfundamentals.org/webgl/lessons/webgl-resizing-the-canvas.html ; https://github.com/nicbarker/clay
12. Backend boundary shaped for WebGPU: explicit render passes, immutable pipeline keys, bind groups (UBO ranges + texture sets), UBO-only uniforms written once per frame with a per-frame ring of buffers, fixed-size resources (`texStorage2D`, `bufferData(size)` + `bufferSubData`), async-only readback, no `getError`/`getParameter` in the frame loop. https://developer.chrome.com/docs/web-platform/webgpu/from-webgl-to-webgpu ; https://www.figma.com/blog/figma-rendering-powered-by-webgpu/ ; https://groups.google.com/g/webgl-dev-list/c/vMNXSNRAg8M
13. Instrumentation is part of the renderer: per-frame counters (draw calls, batches, instances, state changes, texture uploads), CPU phase timers, optional `TIME_ELAPSED_EXT` GPU timer, ring-buffered percentiles, `console.timeStamp` tracks in dev builds, LoAF/event-timing observers for hitch attribution, all drawn by the renderer itself. https://developer.chrome.com/docs/devtools/performance/extension ; https://developer.chrome.com/docs/web-platform/long-animation-frames
14. Testing: fixed-timestep animation clock injectable from tests; Playwright Clock API + `toHaveScreenshot` with per-backend baselines; CI on SwiftShader with the explicit flags; Electron smoke tests via `_electron.launch`. https://playwright.dev/docs/clock ; https://playwright.dev/docs/test-snapshots ; https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/gpu/swiftshader.md

### F.2 OpenGL to WebGL2 port risks, ranked by likelihood of biting

1. Sync calls in the frame loop (`getError`, `getParameter`, `checkFramebufferStatus`, `readPixels`, `finish`, compile-status polling): silent 1 ms+ stalls, worse under ANGLE. Very likely if the C++ code checks errors defensively. https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices
2. Per-draw `uniform*` updates and buffer orphaning idioms: on D3D11 uniforms cost a constant-buffer re-upload; `bufferData(null/size)` zero-fills instead of orphaning. Rewrite to UBO ring + `bindBufferRange` and double-buffered vertex/instance buffers. https://groups.google.com/g/webgl-dev-list/c/vMNXSNRAg8M ; https://groups.google.com/g/webgl-dev-list/c/-Wt6WF9vS4o
3. GLSL differences: `#version 300 es` first line, precision qualifiers (no default float precision in fragment shaders, mediump is really 16-bit on mobile), no dynamic sampler-array indexing, no `double`, no `gl_DrawID` without the extension, vertex attribute aliasing forbidden, texel offsets must be constants. https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf ; https://www.khronos.org/webgl/public-mailing-list/public_webgl/1907/msg00004.php
4. Stencil buffer absent unless `stencil: true` at context creation (and offscreen targets need `DEPTH24_STENCIL8`); a stencil-based clip that "works" in C++ silently no-ops. https://registry.khronos.org/webgl/specs/latest/1.0/
5. Timer queries unavailable outside Chromium (Firefox pref off, Safari flag off) and disjoint events; code that assumes GPU timing exists breaks the perf overlay. https://github.com/mozilla/gecko-dev/blob/master/dom/canvas/WebGLExtensions.cpp ; https://github.com/mdn/browser-compat-data/issues/21351
6. Premultiplied canvas compositing and `alpha:true` default: straight-alpha output shows dark fringes on the page; `alpha:false` has platform-dependent cost. https://limnu.com/webgl-blending-youre-probably-wrong/ ; https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices
7. sRGB framebuffer assumptions: no `FRAMEBUFFER_SRGB` toggle, default drawing buffer is linear-encoded, sRGB FBO renderability must be verified at runtime. https://groups.google.com/g/webgl-dev-list/c/jCIN5lu7wzE ; https://github.com/KhronosGroup/WebGL/issues/3400
8. Texture respecification: re-calling `texImage2D` on a live atlas forces ANGLE to recreate staging and GPU textures; DOM-image uploads mid-frame cause a program switch and pipeline flush. https://github.com/servo/webrender/issues/2960 ; https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices
9. Primitive restart always on and index/data buffer segregation: a quad index buffer using 0xFFFF as a real index, or a buffer reused for both indices and vertices, fails on WebGL2. https://registry.khronos.org/webgl/specs/latest/2.0/#webgl_gl_differences
10. Limits: 4096 max texture size on some devices (100% of reports support 4096, 84% 16384), 16 texture units, 64 KB or 16 KB UBO blocks, 256-byte UBO alignment, 4 MSAA samples guaranteed; blocks not fully backed by a buffer error at draw. https://web3dsurvey.com/webgl2/parameters/MAX_TEXTURE_SIZE ; https://groups.google.com/g/webgl-dev-list/c/-Wt6WF9vS4o
11. No `MapBufferRange`, no program binaries, no texture swizzle, no compute; `getBufferSubData` blocks. https://registry.khronos.org/webgl/specs/latest/2.0/#webgl_gl_differences
12. SwiftShader fallback removed in Chrome 137: WebGL context creation fails on GPU-less CI unless `--enable-unsafe-swiftshader` (plus `--use-gl=angle --use-angle=swiftshader-webgl`) is passed; Electron per-domain 3D API blocking after GPU crashes. https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM ; https://www.electronjs.org/docs/latest/api/app
13. `clientWaitSync` timeouts may be clamped to zero; `MAX_CLIENT_WAIT_TIMEOUT_WEBGL` governs; code that waits synchronously on fences must become polling. https://registry.khronos.org/webgl/specs/latest/2.0/#webgl_gl_differences
14. `WEBGL_multi_draw` missing on Firefox and dual-source blending only as a draft extension: LCD subpixel text and multi-draw batching cannot be relied on. https://github.com/mdn/browser-compat-data/blob/main/api/WEBGL_multi_draw.json
