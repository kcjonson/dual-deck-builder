# Drag service

Date: 2026-09-28. Task: DDB-77 (DDB-55 phase 3). Spec: R9.12 (a to e) in `docs/ui-rendering-spec/09-input-and-focus.md`, R9.1, R9.31, R11.11's `dropActive`.

## Context

DDB-75's dispatcher left drag and drop as a flag: `Component.dragSource`, set by hand, made movement past the threshold cancel a click. Nothing synthesised drag events, so a captured drag could never tell the enemy under it that it was there (capture suppresses that enemy's `pointerenter`, which is R9.12's whole reason). The game has no drag today: a card is played by clicking it and then its target, and the hand layer's doc comment claiming "drag targeting" was wrong. Drag to play, with highlights and a preview line, is DDB-88 in phase 6.

## Decision

`input/DragService.ts`, one per dispatcher, constructed by it and handed out as `context.drag`.

- **Start.** `context.drag.start({ event, source, data, ghost?, threshold? })` from a primary-button `pointerdown` handler; any other button is refused, so a right-click stays a `contextmenu`. Nothing is captured yet (see the departure below). The threshold is the pointer type's `control` token (`drag_threshold_mouse` 4, `drag_threshold_touch` 10) unless given; `dragThreshold(pointerType)` is exported and the dispatcher's touch hold uses it too, so the constants `DRAG_THRESHOLD_MOUSE` and `DRAG_THRESHOLD_TOUCH` are gone. One drag at a time; a second `start` returns false.
- **Active.** The move that crosses the threshold activates the drag before it is delivered: the source captures the pointer unless something already holds it (a touch's implicit captor), so that move already goes to the captor and hovers nothing under it. A press that already fired R9.30's touch-hold `contextmenu`, or was cancelled, never goes active. The ghost (the source by default) then carries a framework-owned `Component.dragOffset`: while it is set the component reads back `layer: 'drag'` and `pointerEvents: 'none'`, and `transformMatrix` puts the offset outside its own transform. The offset is the pointer's travel since the press, in the ghost's parent space, so a rotated or scaled card moves without turning and layout never sees it. The author's own `layer`, `pointerEvents` and `transform` are never written, so a transform tween on the source (a hover lift) keeps running under the drag and keeps where it got to; clearing the offset when the drag ends is the whole restore.
- **Targeting.** Every move hit-tests with the ghost excluded. A change of target fires `dragleave` on the old one and `dragenter` on the new, then `dragover`, all bubbling, as HTML's drag events do. Each dispatch frame also re-targets under a still pointer (enter and leave only), so a target that moves or unmounts under the ghost is noticed without a move.
- **Accept.** `event.accept()` during `dragenter` or `dragover` names `currentTarget` as the acceptor, innermost first. Acceptance belongs to the target it was given for and is collected afresh on each enter. Acceptance given on enter is kept while the pointer stays on the target; once any `dragover` on the target accepts, acceptance follows each `dragover`, so an inner `dragover` accept overrides an outer `dragenter` one and a target that accepts by position (accepting in `dragover`) revokes `dropActive` by not calling it. An acceptor that unmounts is dropped. The acceptor's `dropActive` state flag is set (R11.11, DDB-84's flag set, so its look re-resolves through `onStateChange`); `drag.canDrop` is the source side. An ancestor can accept for its children (the enemy for its portrait), and moving between them keeps `dropActive` without a flicker.
- **End.** The release re-targets first with the drag still current, so a `dragenter` it fires can `cancel()` or unmount its target and be heard. A release over a still-mounted acceptor then fires `drop` at the component under the pointer, bubbling up to the acceptor, then `dragend { dropped: true, dropTarget }` on the source. Any other release fires `dragleave` there and `dragend { dropped: false }` (HTML's order). `pointercancel`, window blur, pause, `releasePointer`, and unmount of the source or ghost end with `dragend { dropped: false }`; unmount delivers `pointercancel` first. `drag.cancel()` does the same for game code (Escape, a right-click chord). `dragend` carries `ghostOffset`, the ghost's travel when the drag ended: the ghost is back in place by then, and a source that animates home (R9.12c) tweens its transform's translate from there to zero.
- **Click and pressed.** An active drag spends its press however it ends, so its release is never a click (R9.30). A drag is not a press either: `pressed` comes off everything from the press target up to the source when the drag goes active, and again however it ends, so a draggable Button never keeps its pressed look through or after a drag. A press that started no drag, or whose drag never passed its threshold, clicks as before, on the component it would have without the drag. This replaces `Component.dragSource`: the drag service now decides what the flag used to, per gesture instead of per component, and the flag is deleted.
- **Tooltips (R9.12e).** `drag.isDragging` and `drag.onDraggingChange(listener)`, which returns its unsubscribe. The tooltip service (DDB-78) reads these; the drag service knows nothing about tooltips. `drag.current` gives `{ source, data, target, acceptor }` while active.
- **Component callbacks.** `onDragEnter`, `onDragOver`, `onDragLeave`, `onDrop`, `onDragEnd`, run by `handleEvent` like the pointer callbacks. `UiDragEvent` carries `source`, `data`, `screen`, `local`, `pointerId`, `pointerType`, and on `dragend` `dropped` and `dropTarget`.

## Options considered

- Keep `dragSource` as a declared flag and have `start` set it: rejected. A flag that must be true before a press, for a drag that may or may not start, is two sources of truth; the dispatcher only needs to know whether this release ended a drag.
- Move the ghost by reparenting it into an overlay root: rejected for now. Promotion to the `drag` layer already escapes the hand's clip (R4.8) and keeps the ghost's coordinates, so there is nothing to translate back on a cancel. A caller that wants a separate ghost passes one.
- Acceptance only through `dragover` on every move (HTML's `preventDefault`): rejected as ceremony. Accepting once on enter is what the game's targets want; `dragover` can still accept when acceptance depends on where in the target the pointer is.
- A per-pointer map of drags for multi-touch: deferred. One drag at a time is what the game and the tooltip suppression need.

## Spec departures

- `start` takes the `pointerdown` event as well as R9.12a's `{ source, data, ghost, threshold }`: the pointer, its type and the press position come from it.
- R9.12a starts a drag "from a captured `pointerdown`"; the service captures when the drag goes active instead. Capturing a candidate would make the source the click target under R9.31, so a button inside a draggable card would lose its click to the card whenever the card could be dragged. Deferred, a candidate drag changes nothing about where a click lands, and an active drag is captured from the move that activates it, so nothing under the ghost hears pointer events.
- R9.12c's "source's `canDrop`" is `context.drag.canDrop` rather than a flag on the source component; R11.11 lists no `canDrop` state.

## Consequences

- No gameplay or pixel change: nothing in the game starts a drag yet. DDB-88 makes hand cards drag sources, with the enemies accepting.
- The DDB-75 departure (the threshold cancels clicks only on drag sources) stands, restated: only on a press that started a drag.
- A button inside a draggable card still starts the card's drag when pressed, since the press bubbles to the card's `pointerdown`. Its click survives a press that never passes the threshold; if it should never drag, it consumes its `pointerdown` so the card never calls `start`.
- A candidate drag is an ordinary press until it goes active, so one that wanders onto a neighbour before crossing its threshold hovers the neighbour, and a release there clicks the common ancestor, not the card (the browser rule DDB-75 chose for plain clicks). With the 4 px token that needs a press within 4 px of the card's edge, but a larger custom threshold, or a fanned hand of overlapping cards, will show it. DDB-88 should either keep the default threshold for hand cards or have a card that started a candidate drag keep its own look until release.
- The touch hold and the drag are exclusive: a finger held long enough for a `contextmenu` (the card detail, in DDB-88) does not then drag.
- The dispatcher hit-tests once more per frame while a drag is active (the still-pointer re-target), and twice on a frame with a queued move. Fine at this tree size; skipping the re-target when the batch holds a move for the drag's pointer is the saving if it ever matters.
- The tree snapshot reports a ghost's `layer` as `drag` and its own `transform`; its `screenBounds` include the drag offset.
- `MountContext` gains `drag`.
