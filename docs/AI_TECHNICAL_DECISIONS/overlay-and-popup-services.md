# Overlay, popup, tooltip, placement, clipboard and asset services

Status: implemented (DDB-78), 2026-09-28
Spec: R12.30 to R12.32, R12.22, R8.21, R3.6a, R3.15, R3.28, R9.13 to R9.15, R9.12e of the [UI rendering spec](../ui-rendering-spec/12-component-catalog.md)
Builds on: [input-dispatcher.md](./input-dispatcher.md), [clock-and-animator.md](./clock-and-animator.md), [mount-context-and-frame-order.md](./mount-context-and-frame-order.md)

## Problem

Chapter 12's catalog needs somewhere for its floating things to live before any of them exists. A dialog, a popover, a menu, a tooltip and a toast stack all paint above the scene, have to be hit-tested in the same order they paint, and close on presses and keys that never reach them. The dispatcher (DDB-75) walked roots in mount order, which on the game page was not paint order (the F5 overlay mounts first and paints last), and left per-root hotkey tables, outside-press dismissal and the popup exclusivity rule to this task. Text fields need a clipboard that works in a browser tab and in a sandboxed Electron renderer, and images need a cache keyed by name over the texture store.

## Decision

**Six services in the mount context**, built by `createMountContext` (`engine/services/`): `placement`, `overlays`, `popups`, `tooltips`, `clipboard`, `assets`. Nothing constructs them anywhere else, so tests get the same wiring the pages do.

**Placement is one pure function (R12.30).** `place({ anchor, size, side, align, offset, gap, viewport })` tries the preferred side, flips when the box overflows there and the opposite side has more room, shifts along the anchor's edge to stay inside the viewport less `gap`, and shrinks the box to the room on the chosen side when neither side fits (`constrained`, which is what a menu reads to scroll). A zero-size anchor is a point. `PlacementService.place` fills in the context's viewport; a caller may pass another rect, which is how the gallery draws every outcome inside one frame.

**Root order is a dispatcher fact with three tiers.** `Dispatcher.addRoot(root, tier)` keeps roots grouped as `scene`, then `overlay`, then `diagnostic`, each in the order its owner supplies, and `raiseRoot` moves one to the end of its tier. `Component.mount(context, { tier })` passes it through. The F5 overlay mounts as `diagnostic`, so it is hit last as it is painted last (as its own domain after a barrier, R3.21), whenever it was mounted. Across layers nothing new was needed: the hit walk already prefers the higher effective layer. The tiers fix the order within a layer, which is the only place root order was ever observable.

**The overlay service owns overlay roots (R8.21).** `overlays.open(content, { layer, modal, dismissOnOutsidePress, inside, consumeOutsidePress, closeOnEscape, onDismiss, onClose })` puts the content under a new viewport-sized `Layer` root in that layer, mounts it in the `overlay` tier, and returns a handle with `close`, `bringToFront`, `dismiss` and a `hotkeys` table. The pages render `overlays.render(draw)` after the scene's roots and before the F5 domain, and read `overlays.roots` for the tree snapshot and lint; the dispatcher's overlay tier is kept in step, so paint and hit order come from one list. Closing detaches the content before unmounting the root, so a dialog can be opened again. `onDismiss` lets a component run its closing fade and close the handle when it is finished; without it a dismissal closes at once. `ScreenManager.navigate` and `SceneHost.unmount` close every popup and overlay (R8.22).

**Dismissal runs through dispatcher observers, not listeners of each service's own.** `dispatcher.addObserver({ pointerDown, pointerMove, hoverChange, keyDown, focusChange })`. `pointerDown` runs before a press is delivered or moves focus, and returning true swallows it: not delivered, no focus change, and its release is swallowed too (no `pointerup`, no click), as a native menu eats the dismissing click whole. `keyDown` runs for a key the focused chain declined, before the scene's hotkey table. The context adds tooltips, then popups, then overlays, and that order is the policy: a press hides a tooltip even when a popup's close swallows it; a popup's Escape is taken before a dialog beneath it could be dismissed; a press a popup swallowed dismisses nothing else.

- Outside press over overlays: topmost first (by layer, then open order), stopping at the first root the press is inside; a root that asks is dismissed, and its `consumeOutsidePress` (default: modal) decides whether the press goes on. A modal root ends the search and consumes a press outside its content. "Inside" is the content unless `inside` names a surface within it: a modal dialog whose content holds a full-viewport scrim passes its panel, so a press on the scrim is outside, dismisses when asked, and is consumed either way (R12.21).
- Keys over overlays (R9.15): topmost first, Escape to the first root that closes on it, then each root's `hotkeys`, and a modal root stops the search, so neither lower roots' nor the scene's hotkeys fire beneath a modal.

**The popup service tracks one exclusive popup (R12.31).** `popups.show({ popup, trigger, anchor, side, align, offset, onClose })` closes the open one (`replaced`) and opens the new one. A popup that is not mounted is opened as an overlay root in `popup` and placed against its anchor; one that is mounted already, a promoted child of its trigger (R3.19), is tracked only. It closes on a press outside the popup and its trigger (consumed unless the target is inside a `popupTrigger` component or the press is secondary, R9.13), on Escape (consumed), on focus moving to something outside the popup and trigger (R9.14), and when a modal root opens (R3.6a). `onClose` hears every close once with its reason. Placement starts from the size the popup had when it opened (`naturalSize`) and applies the placement's size, so a `constrained` placement shrinks the popup to the room and a menu scrolls the rest (R12.11); a tooltip that does not fit is shrunk and clipped the same way. `Component.popupTrigger` is new, beside `dragSource`.

**The tooltip service drives `Component.tooltip` (R12.22).** A tooltip is a title, description and hotkey, a string (a title), or a `factory` whose tree is mounted while shown. States are `idle`, `waiting`, `showing`, `visible`, `hiding`, plus `suppressed` after a press or Escape until the pointer leaves the owner. The owner is the nearest ancestor of the hovered target with a tooltip. The delay counts on the frame clock through a new `UiFrame.requestTick`, R8.17's request-an-update for a service, which runs after the animator and before component updates and only while asked; movement within `hover_move_tolerance` does not restart it. Fades are animator tweens owned by the surface (`dur_fast` in, `dur_tooltip_hide` out). Moving between owners while one is shown swaps content with no delay or fade. The surface is an overlay root in `tooltip` with `pointerEvents: 'none'`, so it never takes input, placed below-right of the pointer (16 px down) or below the owner, with flip and shift. Text content gets a plain `TooltipSurface` sized from measured text; the catalog's Tooltip (DDB-87) replaces it through the constructor's `surface` option. `tooltips.show(owner, { at, fade })` shows at once and `hide()` fades out.

**Clipboard (R12.32, R9.17).** `detectClipboard(window)` prefers the Electron bridge, then `navigator.clipboard` when both halves exist, then text held in the page. The Electron renderer is sandboxed with context isolation, where the `clipboard` module is not available, so `electron/preload.ts` exposes `window.electron.clipboard` over two `ipcMain.handle` channels in `electron/main.ts`. `ClipboardService` never rejects: a refused write returns false, and a refused read (a browser without the read permission) answers with the last text copied through the service, so paste inside the game still works.

**Assets (R12.32).** `assets.acquire(key)` returns a ref with `texture`, `ready` and `release`. The first acquire decodes through the context's loader (`imageUrlLoader()` on both pages); later ones share the texture; the last release frees it through the draw API. A key released before its decode finishes is never uploaded. Textures are created with a `reload` that decodes again, so a lost context brings them back without a CPU copy (R5.33). A failed decode stays failed while held, so a screen asking every frame does not refetch every frame. `ready` is handled internally, so an unread failure is not an unhandled rejection.

**Overlay roots reach the tree snapshot and the lint.** Both pages append `overlays.roots` to the roots they report. Overlay roots are viewport-sized by R8.21, so each overlaps the scene's root; the lint exempts that pair because the snapshot carries each node's effective `layer` (DDB-80).

## Alternatives considered

- **Sorting the dispatcher's roots by root layer**, which DDB-75's note suggested. It changes nothing across layers (the walk already prefers the higher one) and says nothing about two roots in one layer, which is the case that matters; it also would not fix the F5 overlay, which paints last because of a barrier, not a layer. Tiers say what actually decides paint order.
- **The popup as an inline promoted child in the gallery scene**, as R3.19 describes for a select. The lint's `child-outside-parent` has no exemption for promotion, so a menu hanging below its trigger fails the gallery gate. Opening it as an overlay root is R3.6a's own recommendation for popups above a host, and the service supports the inline case for components that want it.
- **The tooltip delay as a tween.** Reduced motion completes a tween on its first tick, which would remove the delay for people who asked for less motion, and `settleAnimations` in the harness would pop hover tooltips into goldens.

## Consequences

- No existing golden moves. The new `overlays` gallery scene has a golden; it is a gallery-only scene (`galleryOnlyScenes` in `src/gallery/registry.ts`), because it opens overlay roots over its host and the developer screen would show them over its own golden. The scene opens its popup and shows its tooltip (without fade) from its first `onLayout`, when the owner is mounted and placed, so a paused harness page and a live one draw the same thing.
- Seams left open: `tooltips.dragActive` is `() => false` until DDB-77's drag service sets it (R9.12e); `tooltips.focusVisibleChange` shows a tooltip from keyboard focus but the dispatcher's focus seam carries no modality, so DDB-76's focus manager calls it when focus becomes visible. The popup service's focus-loss close reads the dispatcher's `focusChange`, which DDB-76 inherits.
- Not done: R3.6a's SHOULD, closing a promoted popup whose ancestor scrolls (DDB-210); `PopupHandle.reposition` exists for an owner whose anchor moves.
- The Electron clipboard handlers answer only the main window's top frame, showing the packaged bundle (`file://` under the renderer directory) or the dev server's origin; the preload follows the window wherever it navigates, and a page it reached could otherwise read the clipboard silently.
- Focus scopes for modal dialogs (R9.20) are DDB-76's; the overlay service records `modal` for it to push one.
