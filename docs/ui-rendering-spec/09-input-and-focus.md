# 9. Input, hit testing, drag and drop, and focus

Status: draft 4 (2026-09-07; revised after all five reviews, see chapter 17)

Hit testing mirrors the paint order in reverse; everything else in this chapter hangs off that one rule, because a pointer event must reach the thing the player sees on top. The chapter defines the event model (pointer, touch, pen, keyboard, and abstract actions), the hit-test walk, bubbling, pointer capture, the drag-and-drop protocol, popup dismissal, keyboard routing with scoped hotkeys, and focus with tab order derived from the tree, focus scopes, focus groups, and directional navigation. Worldsim's event system is the base; the additions are the ones its components had to hand-roll (enter and leave, capture, key bubbling, real focus trapping) and the ones a card game and a controller target need.

Rules are numbered R9.n.

## 9.1 Events

- R9.1 Pointer events: `pointerdown`, `pointerup`, `pointermove`, `pointerenter`, `pointerleave`, `pointercancel`, `wheel`, `click`, and `contextmenu`. Drag events (R9.12): `dragenter`, `dragover`, `dragleave`, `drop`, `dragend`. Keyboard events: `keydown`, `keyup`, `char`. Abstract actions (R9.27): `activate`, `cancel`. Every event carries type, timestamp, `target`, `currentTarget`, and a `consumed` flag with `consume()`. Pointer events additionally carry screen and local position (local filled in as the event descends, with transforms inverted), `pointerId`, `pointerType` (`mouse`, `touch`, `pen`, `virtual`), `isPrimary`, `pressure` (on a mouse-only platform these four default to 0, `mouse`, true, and 0.5 while pressed and need no platform plumbing), `button`, the `buttons` mask, modifiers, and for `wheel` normalised deltas on both axes. Keyboard events carry the key name, `codePoint` for `char` (a Unicode scalar value; the `keydown` for a printable key precedes its `char` in the same frame), modifiers, and `repeat`.
- R9.2 Platform events are queued as they arrive and dispatched at the start of the next frame in arrival order, with consecutive `pointermove` events per pointer coalesced (the last position wins; intermediate positions are available on the event for gesture consumers). Before the first hit test of a frame, and after any dispatch that dirtied layout, the dispatcher runs layout for dirty subtrees (free when clean) so hit testing always sees current geometry; a dialog opened by one event is therefore solid before the next event in the same burst. When the platform is polled rather than event-driven (worldsim's GLFW loop) at most one down and one up per button per frame are generated, and the injection API (chapter 13, R13.36) respects the same limit.
- R9.3 Wheel deltas are normalised to logical pixels per axis (pixel mode as is, line mode times 16, page mode times the scroller's viewport) and used directly as scroll distances; no per-notch constant exists, so trackpads scroll smoothly. Shift with a vertical-only delta swaps the axes. The sibling engine multiplied raw browser pixel deltas by 30 and scrolled 3000 pixels per notch.
- R9.30 `pointerdown` and `pointerup` fire for the first button pressed and the last released on a pointer; chorded buttons arrive as `pointermove` with `button` set and `buttons` updated (Pointer Events Level 3). Only the primary pointer synthesises `click` and drives hover; non-primary pointers deliver down, move, up, and cancel for multi-touch consumers. `pointercancel` means the platform or the framework abandoned the gesture (scroll takeover, palm rejection, window blur, capture loss): the target and any captor MUST reset pressed and drag state without firing `click`, `onChange`, or `drop`. `contextmenu` is synthesised on a secondary-button release, and on a 500 ms touch hold under the drag threshold.

## 9.2 Hit testing and dispatch

- R9.4 Dispatch begins with a hit-test walk that finds the topmost component under the point: layers from top to bottom (chapter 3, R3.5), and within a layer the reverse of submission order (last painted first), descending into a component's children only when the point is inside the component's clip (chapter 4, R4.12), after removing the component's content offset (R4.11) and applying the inverse of its transform (chapter 8, R8.26), and only when its `pointerEvents` is not `none` or `unit`. A component is reported as `target` when its `pointerEvents` is `auto` or `unit` and `containsPoint` holds. `containsPoint` decides self-hit only; it never gates descent. `dispatcher.hitTest(screenPoint, { exclude })` is public and returns the same answer for drag targets and tests.
- R9.5 Disabled components are hit-testable (they occlude what is beneath them, as CSS elements do) but do not receive `click` or `activate`, do not change hover state visually beyond their disabled style, and cannot take focus.
- R9.6 The event is delivered to the target, then bubbles to each ancestor in turn until consumed or the root is reached. There is no capture phase in the baseline; an implementation MAY add one. The bubble path is the ancestor stack of the hit-test walk, so no parent pointer is needed for it. Worldsim recorded a single top-down pass with no bubbling as a decision (a flat UI, no default actions to prevent, z sorting for layering); its dialogs and menus then had to be dispatched first by hand in every scene once popups nested and dialogs needed Escape. The bubble gives a dialog its Escape and its click-outside without that; 9.10 answers the recorded reasons.
- R9.7 A modal dialog's scrim is a component covering the viewport in the `modal` layer with `pointerEvents: auto` that consumes every pointer event it receives (chapter 3, R3.29). Its hit-testability is independent of its alpha, so it blocks from its first frame of fade-in. No global "modal capture" state exists.
- R9.8 `pointerenter` and `pointerleave` are derived by the dispatcher from consecutive hit tests and delivered without bubbling to the components whose containment changed: `pointerleave` innermost first, then `pointerenter` outermost first. `hovered` is true on the target and on every ancestor of the target (containment semantics, as CSS `:hover`), so a button is hovered while the pointer is over its own label. Components MUST NOT recompute hover from `containsPoint` every frame. Worldsim's widgets set hover on a move event, which is right, but its application synthesises a move event every frame whether or not the pointer moved and nothing derives enter and leave centrally, so in effect every widget's `containsPoint` runs every frame; the fix is on both sides. The tooltip service uses the innermost hovered component with a `tooltip`. Hover-only behaviour (enter without a press, tooltip delay, hover visual state) applies only to pointer types that can hover.
- R9.9 Hover MUST be re-evaluated when layout moves content under a stationary pointer (after a scroll, a layout change, a screen change, or a capture release), not only on pointer motion.
- R9.31 `click` is synthesised on `pointerup` and targeted at the nearest common inclusive ancestor of the `pointerdown` target and the `pointerup` target (UI Events), or at the capturing component when one captured; it bubbles from there. No click is synthesised when the pointer moved more than the drag threshold (R9.12), when the press was cancelled, or for non-primary buttons. A press that is consumed still produces a click: consumption stops bubbling of the press, not the gesture.

## 9.3 Pointer capture

- R9.10 `capturePointer(pointerId)` from a `pointerdown` handler routes every event of that pointer to the capturing component as `target`, bubbling from it, with no hit test, until `releasePointer()`, the pointer's `pointerup`, or a `pointercancel`. Capture is per pointer. A `touch` pointer is implicitly captured by its `pointerdown` target until up or cancel. Boundary events for a captured pointer are computed against the captor only. On release the dispatcher fires `lostpointercapture` on the captor and re-evaluates hover from the current position (R9.9), delivering `pointerleave` to the captor if the pointer is outside. Unmount, `visible: false`, or `enabled: false` of the captor, and window blur, release capture and deliver `pointercancel` to it first. Sliders, scrollbar thumbs, text selection, and card dragging use capture; worldsim's drags kept their own flags and worked only because nothing above them consumed the release.
- R9.11 Press and click semantics for a button-like component: `pointerdown` inside sets pressed and captures; `pointerup` releases capture, clears pressed, and fires `click` only if the pointer is still inside; a release outside fires nothing. A `pointerdown` that opens a popup captures the opening press so the following `pointerup` cannot activate the item under it (worldsim's context menu kept an `ignoreNextMouseUp` flag for this).

## 9.4 Drag and drop

- R9.12 Drag and drop is a dispatcher service, specified in the sub-rules below. Without it a captured drag could never highlight the enemy under the card, because capture suppresses that enemy's `pointerenter`. An implementation whose applications have no drop targets (worldsim's drags are slider and scrollbar drags, not drag-and-drop) scores the service not applicable under chapter 14, R14.9.
- R9.12a Start and threshold: a component starts a drag from a captured `pointerdown` by calling `context.drag.start({ source, data, ghost, threshold })`. The drag becomes active once the pointer has moved `threshold` logical pixels (tokens `drag_threshold_mouse`, default 4, for mouse and pen; `drag_threshold_touch`, default 10); until then the gesture is still a candidate click, so click-to-select and drag-to-target coexist on one card.
- R9.12b Ghost and targeting: when active, the ghost (default the source itself) is promoted to the `drag` layer with `pointerEvents: none` and follows the pointer with the press offset; on every move the dispatcher hit-tests with the ghost excluded and synthesises `dragenter`, `dragover` (each move), and `dragleave` on the component under the pointer, bubbling, carrying `data`.
- R9.12c Accept and drop: a component accepts by calling `event.accept()` during `dragenter` or `dragover`, which sets its `dropActive` state (chapter 11) and the source's `canDrop`. On release over an accepting target the dispatcher fires `drop` on the target, then `dragend` on the source with `{ dropped: true, target }`; otherwise `dragend` with `{ dropped: false }` and the source animates home if it chooses.
- R9.12d Cancellation: `pointercancel`, loss of capture, or unmount of the source ends the drag with `dragend { dropped: false }`.
- R9.12e Tooltips are suppressed while a drag is active.

## 9.5 Popup dismissal

- R9.13 A `pointerdown` outside an open popup closes it. Menus, selects, and context menus consume that press (native desktop behaviour, worldsim's choice), with two exceptions: the press is not consumed when its target is a component flagged `popupTrigger` (so one press switches from one open select to another), and a secondary-button press outside closes without consuming (so a right-click elsewhere opens a new context menu at the new point). Tooltips and non-modal overlays never consume anything.
- R9.14 Popups also close on focus loss (except focus moving into the popup itself) and on Escape; only one popup of the exclusive kind (menu, select, context menu) is open at a time, enforced by the popup service in the mount context rather than by focus theft between components.

## 9.6 Keyboard routing

- R9.15 Keyboard events are delivered to the focused component, bubble through its ancestors to its root, then to that root's `hotkeys` table, then to each overlay root's table from the topmost down until a modal root is reached (a modal root stops the search: hotkeys of roots beneath a modal never fire), and finally to the scene's table. A component that accepts text (a text input, a search field) consumes every `keydown` and `char` it receives while focused except Tab, Escape, and bound modifier chords, so a printable hotkey never fires from inside a field. Worldsim routed keys only to the focused component; dialogs got Escape only because the dialog itself took focus.
- R9.16 Tab and Shift+Tab move focus (9.7) and are consumed before reaching components, unless the focused component declares it handles Tab.
- R9.17 Text input: a `char` event carries a code point after the platform's composition; `keydown` carries the key name, modifiers, and `repeat`. A text field MUST support caret movement (arrows, Home, End), selection with Shift and with pointer drag, Delete and Backspace, clipboard cut, copy, paste through the context's clipboard service, and select-all. Key repeat is delivered as repeated `keydown` with `repeat` true.
- R9.27 `activate` and `cancel` are abstract events synthesised from the first (non-repeat) Enter or Space and from Escape, from controller confirm and cancel buttons, and from the injection API; components handle `activate` instead of checking key names, and buttons ignore repeats. The mount context exposes `inputMode` (`pointer`, `keyboard`, `controller`), set by the platform shell from the last input source, so components MAY change affordances (show key hints, hide hover-only UI). A platform shell with a controller drives a `virtual` pointer for free-cursor mode and directional focus (R9.26) for navigation mode.

## 9.7 Focus

- R9.18 Focus is a capability a component opts into with `focusable: true` and an optional `tabIndex`. Tab order is derived from the tree, never from registration time: within the active scope root, focusables with `tabIndex > 0` come first in ascending `tabIndex` (ties in tree order), then every other focusable in depth-first tree order (children in insertion order, not `zIndex` order); the order is computed lazily and cached until the tree, a `tabIndex`, or a `focusable` flag changes. Registration on mount exists only so the manager knows the set and can clear focus on unmount. `canReceiveFocus()` (effectively visible, effectively enabled, focusable) filters navigation. Worldsim ordered by registration time, which equals tree order only for trees built once and in order.
- R9.19 `focusNext()` and `focusPrevious()` wrap around the active set and skip components that cannot receive focus. With nothing focused, Tab lands on the first focusable in the active scope.
- R9.20 A focus scope is a subtree root. Pushing a scope (a modal opening) makes that root the active scope; the order is derived from its subtree on demand, so no refresh step exists; the first focusable in the scope takes focus; popping restores the previously focused component if it is still registered and can receive focus. Worldsim implemented and tested scopes and then never populated a dialog's set, so Tab cycled the whole background.
- R9.21 Unregistering (on unmount) removes the component from every scope and clears current focus without invoking focus callbacks on it; the component may be mid-teardown. Worldsim crashed on a pure-virtual call before adopting this rule.
- R9.22 Programmatic `focus()` on any focusable sets focus and fires `onBlur` on the previous and `onFocus` on the new component in that order; it keeps the current focus-visible modality, except that text-entry components always draw their caret and focus border.
- R9.23 A `pointerdown` focuses the nearest focusable inclusive ancestor of the target (so a press inside a select's menu keeps the select focused); if there is none, focus is cleared, unless the press was consumed by a component that called `event.preventFocus()` (scrollbars, drag handles). Focus moved by a pointer clears `focusVisible`; focus moved by Tab, arrows, directional navigation, or `activate` sets it. The focus ring is drawn only when `focusVisible` (chapter 11), which is the `:focus-visible` rule the design language specifies and worldsim only approximated by never focusing buttons on click.
- R9.28 At the end of each frame's layout the focus manager checks `canReceiveFocus()` on the focused component; if it no longer holds (hidden, disabled, unmounted), focus is cleared with `onBlur` and, when a scope is active, moved to the scope's first focusable.
- R9.29 A container with `focusGroup: true` is a single Tab stop: Tab enters it at its last active child (or the first), arrows and Home and End move `activeChild` within it (`orientation`: `horizontal`, `vertical`, or `both`; wrap optional), `activate` fires the active child's activation, and Tab leaves it. Lists, radio groups, tab bars, menus, and toolbars are focus groups; their children are not in the sequential Tab order (the ARIA roving-tabindex pattern).
- R9.26 `focusDirection(direction)` for `up`, `down`, `left`, `right`: from the focused component's `screenBounds` (or the scope's first focusable when nothing is focused) select the candidate in the active scope whose bounds lie in the half-plane of the direction, minimising the distance along the direction plus twice the distance across it, with a bonus for cross-axis overlap; components MAY override with explicit neighbours (`focusUp`, `focusDown`, `focusLeft`, `focusRight`). Arrow keys route to the focused component first (R9.24) and fall back to `focusDirection` when unconsumed. Directional focus sets `focusVisible`. This is what a controller's D-pad drives; the game's design document requires it.
- R9.24 Focused components receive `keydown`, `keyup`, and `char` first; unhandled keys bubble (R9.15). Activation keys: `activate` fires buttons; arrows move sliders, tab bars, menus, tree views, and focus groups; Escape closes popups and dialogs; Home and End jump.

## 9.8 Scroll routing

- R9.32 The first wheel event of a sequence picks the innermost scroller under the pointer that can move in that direction; subsequent events within 150 ms of the last stay latched to it even at its end (no chaining mid-gesture); a latched scroller consumes its events, and passes on the first event of a sequence it cannot move on. Chapter 4, R4.13 and chapter 12, R12.20 defer to this rule.

## 9.9 Injection and testing

- R9.25 The injection API of chapter 13 (R13.35) feeds the same queue and dispatcher, with `pointerId` and `pointerType` on pointer verbs and a `cancel` verb. Tests drive components by injecting events on a mounted root, never by calling a component's handler directly, so the hit-test, capture, and bubble rules are exercised.

## 9.10 Rationale

Worldsim's single top-down pass with consume-to-stop is simple and its widgets' state machines are worth copying line for line (the button state machine, the slider drag, the dialog's dismissal table). What it lacked shows up as duplicated code: every widget recomputed hover from a move event synthesised every frame, every drag kept its own flag, every scene hand-ordered dispatch so popups won, two dropdowns closed each other by stealing focus. A hit-test pre-pass mirroring the paint walk, enter and leave events, capture, and a light bubble phase remove all four, and they are what every browser and every game UI toolkit with popups (Unity UI Toolkit, Godot, egui, PixiJS) provides. Worldsim's event-system document records no bubbling as a decision with three reasons: the UI is flat, there are no default actions to prevent, and z sorting handles layering. None of the three held by mid-2026: menus nest inside selects inside dialogs, Escape and click-outside are default actions a dialog wants from its descendants, and z sorting is the thing chapter 3 removes from dispatch. A native implementation can still land the change in the maintainer's order (layer-ordered dispatch first, central enter and leave second, one captor third, the bubble last) because each step is observable on its own; the conformance row for the bubble stays no until the last step. The review added the parts the first draft left implicit and a card game cannot do without: an explicit target model so a button with a label child works, the drag protocol (HTML drag events, Unity's DragEnter and DragPerform, Flutter's Draggable and DragTarget all converge on synthesised enter, over, leave, drop), touch and pen semantics from Pointer Events Level 3, scoped hotkeys, tree-derived tab order (HTML's sequential focus navigation order), focus groups (the ARIA roving-tabindex pattern), focus fixup, and directional navigation (Android's D-pad focus search, Unity's automatic navigation) for the controller target the game's design document names.

## 9.11 Required tests

- Hit order: overlapping siblings, a promoted popup over base content, a scrolled-out child (not hit), a disabled button (hit, no click), a `passthrough` container's padding (not hit), a `unit` widget's label (widget is the target), a `none` ghost (ignored), a rotated card (hit within its rotated quad).
- Bubble: an unconsumed `pointerdown` on a dialog's content reaches the dialog; a consumed one does not; a scrim at opacity 0.01 blocks from its first frame.
- Enter and leave: moving from A to B produces `leave(A)` then `enter(B)`; a button is `hovered` while the pointer is over its label; scrolling content under a still pointer updates hover.
- Click: down on a button's label, up on its icon, produces one click on the button; down then move beyond the threshold produces no click.
- Capture: a slider drag continues when the pointer leaves its bounds and ends on release anywhere with `lostpointercapture`; a button pressed then released outside does not click; unmounting the captor delivers `pointercancel`.
- Drag: below the threshold a release is a click; above it, the enemy under the ghost receives `dragenter`, accepts, shows `dropActive`, and receives `drop`; `pointercancel` mid-drag fires `dragend { dropped: false }`.
- Touch: `pointerdown` implicitly captures; no hover state; a 500 ms hold fires `contextmenu`.
- Popup opened on press does not activate an item on the same gesture's release; a press on another trigger switches popups in one press.
- Focus: tab order follows tree order even when children are inserted out of order; `tabIndex > 0` comes first; wrap-around; disabled skipped; modal scope traps Tab and restores focus on close; unmounting or hiding the focused component moves focus per R9.28 without callbacks on the removed one; `focusVisible` true after Tab, false after click, unchanged after programmatic focus; a press in a select's menu keeps the select focused; a focus group is one Tab stop with arrow movement inside.
- Directional focus picks the nearest candidate in the pressed direction and respects explicit neighbours.
- Keyboard: Escape closes the topmost popup, then the dialog, then reaches the root hotkey table; a hotkey bound to a printable key does not fire while a text field is focused; a hotkey of a root beneath a modal does not fire; held Enter activates once.
- Wheel: one line-mode event scrolls 16 logical pixels; a latched inner scroller keeps events for 150 ms at its end.
