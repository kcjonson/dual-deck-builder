# 8. Object model

Status: draft 4 (2026-09-07; revised after all five reviews, see chapter 17)

The retained tree is the developer-facing API: persistent component objects with properties, children, and callbacks, in the style of a DOM built from constructor arguments rather than markup. It is deliberately thin. Its job at draw time is to walk itself in the order chapter 3 defines and re-issue immediate draw calls (chapter 2); nothing is cached on the GPU between frames. Its job the rest of the time is to hold state, run layout (chapter 10), route input (chapter 9), and drive animation.

Rules are numbered R8.n.

## 8.1 One interface for everything drawable

- R8.1 Every node in the tree, whether a leaf shape or a composite widget, implements one interface: `render()`, `handleEvent(event)`, `containsPoint(localPoint)`, the layout protocol `measure(availableWidth, availableHeight)` and `assignSize(width, height)` (worldsim names the latter `setLayoutSize`), read-only `bounds` (8.3), and the properties of R8.2. `render()` emits the component's own draws only; the framework visits children in local order (chapter 3, R3.11), and a component MUST NOT render its children itself. The sibling engine's leaves each recursed into their children, so nothing could sort siblings, push layers, or apply effective opacity uniformly. Worldsim's design-system primitives (panel, badge, avatar, keycap, divider, stat, segmented control) were plain structs with a `render()` and no place in the tree, so they could not be laid out, linted, or clicked, and its button, select, dropdown, and toast stack render their icon, menu, chevron, and toasts directly from their own `render()`, outside the sorted walk; an implementation MUST NOT carry either split forward.
- R8.2 Properties on every component, with defaults:
  - identity and visibility: `id` (string or null), `visible` (true), `enabled` (true), `opacity` (1);
  - ordering: `layer` (inherit; chapter 3), `zIndex` (0; local order among siblings);
  - geometry: `position`, `size`, `margin` (per side `{ top, right, bottom, left }`, a number as the uniform shorthand; default 0; per-side margin is a specification addition, worldsim's is one number), `transform` (identity; R8.26), `widthMode` and `heightMode` (`fixed`; chapter 10), `fillWeight` (1), `minSize`, `maxSize`, `aspectRatio`, `alignSelf`, `positioned` (`flow`), `anchor`, `pivot` (chapter 10);
  - interaction: `pointerEvents` (R8.29), `focusable` (false), `tabIndex`, `focusGroup`, `cursor` (`default`), `tooltip` (null; chapter 12), `popupTrigger` (false);
  - callbacks (all optional): `onPointerDown`, `onPointerUp`, `onPointerMove`, `onPointerEnter`, `onPointerLeave`, `onClick`, `onContextMenu`, `onWheel`, `onKeyDown`, `onKeyUp`, `onFocus`, `onBlur`, `onDragEnter`, `onDragOver`, `onDragLeave`, `onDrop`, `onDragEnd`, `onLayout`. The base `handleEvent` invokes the matching callback before its own default handling; subclassing and overriding `handleEvent` remains available for composites.
- R8.3 Effective visibility, enabled state, opacity, and layer are derived from the component's own value and its parent's effective value (conjunction, product, or inheritance). An invisible component and its subtree are skipped by render, input, update, and flow layout. A disabled container disables its descendants for input and focus but still draws them in their disabled style. `opacity: 0` lays out and draws nothing, is skipped by hit testing as if `pointerEvents: none`, keeps focus and focusability, and is not `hovered` (chapter 3, R3.27).
- R8.4 Components have a debug type name and the optional `id`; both appear in the tree snapshot (chapter 13). Ids are plain strings owned by the component, SHOULD be unique within a root, and SHOULD be set on every interactive component so tests and the lint can address it by name rather than by index. Every mounted component exposes `parent`, `root`, `isMounted`, and `context`; a root exposes `findById(id)`.

## 8.2 Containers and children

- R8.5 A container holds children in an insertion-ordered list with `addChild(child)`, `insertChild(index, child)`, `moveChild(child, index)`, `removeChild(child)`, and `clearChildren()`. Each child has exactly one parent and a parent back-reference. `moveChild`, and `insertChild` of a child already mounted under the same root, move it without unmounting: no `unmount` or `mount`, focus and hover kept, running transitions continue. Re-parenting across roots removes (unmounts) first.
- R8.6 The children list is never reordered by the framework and contains exactly what the caller added: library containers MUST NOT insert implicit children (a background, a content layer), and `getChildren()` never returns the render-order view. Rendering and hit testing use a separately maintained order view (chapter 3, R3.13). `zIndex` changes mark that view dirty and nothing else. The sibling engine's panel inserted two hidden children and redirected child access around them, and ten call sites indexed `children[n]` on the assumption.
- R8.7 `removeChild` and `clearChildren` unmount the removed subtree (R8.15). Worldsim has no remove at all (clear-and-rebuild only); the sibling TypeScript engine had a remove that did not unmount and leaked input registrations for every rebuilt panel.
- R8.27 `reconcileChildren(items, { key, create, update, remove })` performs a keyed diff of a container's children against model data: children whose key is still present are kept and passed to `update(child, item)`, new keys are created and inserted, keys no longer present are removed (unmounted after the optional `remove(child)` callback returns, so an exit animation can run), and the final order matches `items` through state-preserving moves. Implementations SHOULD provide it (it is required for the deck builder, whose hand, log, and shop are data-driven lists; a native implementation whose documented idiom is clear-and-rebuild MAY omit it and report the row); game code SHOULD use it for any list driven by data (a hand of cards, a log, a shop), never clear-and-rebuild, which destroys hover, focus, tooltip timers, and in-flight animations on every change.
- R8.8 Composite widgets MAY build their visuals from child shapes or MAY issue draw calls directly in `render()`; both are conforming, and whatever they draw follows chapter 3, R3.18 internally. A component's `bounds` cover its layout box; drawing MAY extend past it as ink overflow (shadows, glows, focus rings, the pressed 1 px nudge). Ink overflow does not affect layout, hit testing, or the lint; it is clipped by clipping ancestors like everything else; a component reports `inkExtent`, the maximum outset it may draw, so that scroll containers and dialogs SHOULD inset their clip by the largest `inkExtent` of a direct child when they have padding to spare and so the snapshot can carry `inkBounds`.
- R8.9 Popups a widget owns (a select's menu, a component's tooltip) are children of that widget with a promoted layer (chapter 3, R3.19), so they appear in the tree snapshot under their owner and receive input through the normal dispatch.

## 8.3 Geometry conventions

- R8.10 Coordinates are local to the parent's content box, in logical pixels, y down (a change for worldsim, whose positions are absolute: its containers do not translate their children, so every screen positions in window space and only its scroll container and dialog offset their content). A component's `position` is the origin of its margin box in that space (for `positioned: 'absolute'` children, an offset from the anchor; chapter 10, R10.15). Its content box is the margin box inset by `margin` on each side. Reported `bounds` (for layout, lint, and the snapshot) is the margin box; `margin` is reported alongside so consumers can derive the content box.
- R8.11 `size` is the content size. A container's reported width is `size.width + margin.left + margin.right`. The margin-box reporting is worldsim's convention, kept because its layout engine, lint, and every fixture assume it; the parent-local coordinate space of R8.10 is not.
- R8.12 Hit testing uses the content box, with half-open edges (`x >= left && x < right`), after applying the inverse of the component's `transform`. Worldsim mixed margin-box (button, slider) and content-box (scroll container) hit tests per component, all with closed edges; the base implementation MUST provide the one convention and components override `containsPoint` only for non-rectangular shapes.
- R8.13 Every mounted component exposes read-only `screenBounds` (its content box in viewport logical pixels, computed by the framework during layout from ancestor origins, content offsets, and transforms; the axis-aligned bounds when a transform rotates it), `screenQuad` (the four transformed corners), `localToScreen(point)`, and `screenToLocal(point)`. These are valid after the frame's layout. Components MUST NOT read the window or canvas size and MUST NOT accumulate ancestor positions themselves; they use these accessors or the viewport in the mount context. The sibling engine had thirteen direct window-size reads in screens and a root sized from the window rather than from the viewport it was mounted in.
- R8.26 `transform` is `{ rotate (radians), scale (number or [sx, sy]), translate ([dx, dy]), origin ([ox, oy] as fractions of the content box, default the centre) }`, identity by default. Layout ignores it (CSS `transform` semantics: the layout box is untransformed). Render pushes it after the parent's origin and content offset; the hit walk applies the inverse to the point before `containsPoint` and before descending; clips under a rotated transform follow chapter 4, R4.7; the lint uses the untransformed box; the snapshot emits `transform` when it is not identity. Setting `transform` invalidates nothing in layout. A fanned hand is cards with `rotate` and `scale`; a hover lift is a `translate` tween.

## 8.4 Lifecycle

- R8.14 Construction sets properties only; it MUST NOT register with input, focus, or tooltip services and MUST NOT allocate GPU resources. Those happen on mount.
- R8.15 `mount(context)` is called when a subtree is attached to a rooted tree, top-down, with the mount context (R8.28); `unmount()` is called when detached, bottom-up, and MUST release every registration made on mount, cancel the component's tweens, and release any pointer capture it holds. `unmount()` on an unmounted subtree is a no-op; `addChild` on a mounted parent mounts the child at once with the parent's context; building a subtree before it is mounted is the normal case. There are no service singletons reachable from a constructor; worldsim's focus manager singleton throws if a focusable is built before the app wires it, and tests had to install one per fixture.
- R8.16 Per frame, in this order: input dispatch (chapter 9; queued platform events dispatched against current geometry, with layout run on demand for dirty subtrees before each hit test), `update(dt)` for components that requested it (R8.17), layout of dirty subtrees (chapter 10), render (chapter 3), then the tree snapshot if requested and the frame statistics. Render never runs layout implicitly. Worldsim ran layout lazily inside `render()`, which made positions valid only after a render and forced tests to render to lay out.
- R8.17 A component receives `update(dt)` on the next frame only after calling `requestUpdate()` (one-shot, in the manner of `requestAnimationFrame`); animations re-request each frame. The frame calls `update` on the requested set, skipping components that are unmounted or in an invisible subtree, before layout. `dt` is clamped (chapter 13, R13.9). A static screen therefore costs nothing in the update phase. Layers 2 to 4 and game UI code MUST NOT use platform timers (`setTimeout`, `setInterval`, wall-clock reads); all timing derives from the context clock or `dt`, or a frozen test clock (chapter 13, R13.37) cannot make a frame deterministic.
- R8.28 The mount context carries the services of chapter 1, R1.6, plus one `clock` (frame time, `dt`, `now`; injectable and freezable for tests, chapter 13, R13.37) and one `animator`. `animator.tween({ from, to, duration, ease, onUpdate, onComplete, owner })` returns a handle with `cancel()`; duration and ease default to the motion tokens; under reduced motion a tween completes on its first tick; tweens tick in the update phase in creation order and are cancelled when their owner unmounts; a tween retargeted mid-flight starts from its current value (CSS reversing semantics), so a quick hover in and out never snaps. Style transitions (chapter 11, R11.13), the dialog entrance, the meter fill, the toast lifecycle, and hover lifts are built on this primitive.
- R8.21 A scene owns its main root and HUD roots. Overlay roots (dialogs, toast stacks, screen transitions, anything opened through `context.overlays.open(component, { layer })`) are owned by the overlay service in the mount context, which mounts them as roots after the scene's roots in open order, walks them for render, hit testing, snapshot, and lint, and removes them when the component reports `finished` (a dialog after its closing fade; a toast stack never). A root's layout box is the viewport rectangle from the mount context (logical size after `uiScale`); a root stack with `fill` on both axes therefore fills the viewport and a viewport change re-lays out every root through the ordinary invalidation path with no screen code involved. Geometry is invalid until the first layout after mount; components that need their size use `onLayout(bounds)` (fired after each layout in which their bounds changed), never `mount`.
- R8.22 Screen transitions unmount the outgoing roots before mounting the incoming ones (the ScreenTransition component of chapter 12 orders fade out, unmount, mount, one layout, fade in, and blocks input while active), so no registration survives a screen change. The sibling engine once had buttons of a previous screen still clickable for exactly this reason; it fixed that with an unmount chain, which this rule generalises.

## 8.5 Invalidation

- R8.18 Changing a property that affects size or position (`size`, `margin`, sizing modes, `visible`, text content, font, `minSize`, `maxSize`) marks the component dirty and propagates up through parents to the nearest relayout boundary: the nearest ancestor whose sizing modes are both `fixed`, or a root. Layout runs from that boundary downward once per frame before render (and on demand before a hit test, R8.16). Changes to `position` of an absolutely positioned child, `zIndex`, `layer`, `opacity`, `transform`, `cursor`, interaction state, and style values that do not affect measurement (colours, shadows) MUST NOT invalidate layout; `zIndex` invalidates the render-order view only. Worldsim required callers to invalidate the owning container by hand, and its own log records the bug that produced ("hug container freezes at last measured size").
- R8.19 Rendering is a full re-emit every frame in the baseline. An implementation MAY cache per-component draw data (glyph quads, tessellated icons) keyed on the properties that produced it; it MUST NOT cache across frames anything that depends on ancestors (screen position, clip, opacity, layer) unless it also invalidates on ancestor change. An implementation MAY go further and retain the sorted draw list of a subtree between frames, re-emitting only when the subtree's dirty flags say something changed (PixiJS v8's "build instructions, upload once, reuse when unchanged" model); that is an optimisation behind the same API, not a different model.
- R8.20 There is no per-node GPU retention in the baseline. A screen with thousands of static nodes MAY be promoted to an off-screen composite (chapter 3, R3.26) as an optimisation; that is the only retained-geometry path in this specification.

## 8.6 Hit-testability

- R8.29 `pointerEvents` on every component: `auto` (the component's own content box is a hit target and children are hit-tested; default for leaves and widgets), `passthrough` (own box is transparent to hits, children are hit-tested; default for `Container` and `Stack`), `unit` (own box is the target and the walk does not descend; default for composite widgets whose internals are implementation detail: Button, Select, Slider, TabBar, ListRow, Checkbox, Toast; the widget MAY still route internally), `none` (neither self nor children: drag ghosts, decorative overlays, scrims that must not block). Hit-testability is never derived from whether a component draws something; a transparent scrim that must block input is `auto`.

## 8.7 Authoring API shape

- R8.23 Constructors take a single named-argument object: `new Button({ label, size, tone, onClick })`. Properties are exposed as accessors (`button.label = 'x'`), not `get`/`set` method pairs, in languages that have property accessors; in C++ the `getWidth`, `setPosition` method style stays. Both are the sibling project's stated conventions and worldsim's `.Args{}` designated-initialiser style is the same idea in C++.
- R8.24 Style properties use CSS names in camelCase from the closed set of chapter 11, R11.14, with values in logical pixels, colour strings, or token references. The sibling engine already exposes this surface at about 190 call sites; keep the names and make every accepted one work.
- R8.25 Callbacks are properties. A callback fires synchronously, inside dispatch, immediately after the component has completed the state change it describes (the value is already updated when `onChange` runs; the menu is already closed when `onSelect` runs). A callback MAY mutate the tree, set properties on its own component (re-entrancy: a component MUST accept a property set from inside its own callback and MUST NOT fire the callback again for it), open popups, or move focus; it MUST NOT invoke the dispatcher recursively. Events passed to callbacks carry `consume()`, and a callback that consumes stops the bubble. Worldsim's callbacks are synchronous and every ported behaviour test assumes it.

## 8.8 Rationale

Worldsim's interface is small enough to port verbatim and is exactly the surface its layout engine, lint, and serializer need; that is why it is kept. Its structural defects, no mount lifecycle (constructor-time singleton registration), no upward invalidation, no remove, and layout inside render, are the changes here, and all were flagged in its own log. The review added what a card game needs on top and what every surveyed toolkit provides: an explicit hit-testability property (CSS `pointer-events`, PixiJS `eventMode`, Unity `pickingMode`), a transform that layout ignores, keyed reconciliation with state-preserving moves (the DOM's `moveBefore`), an update opt-in and a tween primitive, ink overflow distinct from the layout box (Flutter's paint bounds), read-only screen geometry, and synchronous callbacks. The margin-box convention is unusual next to CSS but consistent, tested, and cheap; changing it would invalidate every layout fixture for no visible benefit.

Arena storage and generational handles are C++ concerns; in a garbage-collected language a child is a reference. The invariant that survives is R8.6. Storage is implementation-defined: a bump-allocated arena that cannot free MAY implement `removeChild` as a tombstone (the slot is skipped by the children and order views and reclaimed on `clearChildren`), which keeps handles valid, and `moveChild` and `insertChild` then reorder the order view rather than the storage. Two invariants a native implementation has to state: unmount runs before the arena's destructors, and the mount context outlives every component.

## 8.9 Required tests

- Effective visibility, enabled, opacity, and layer propagate; invisible subtrees are skipped by render and hit test; `opacity: 0` keeps focus and is not hit.
- `removeChild` unmounts and releases focus, capture, tweens, and input registrations; `moveChild` and same-root `insertChild` keep hover, focus, and a running tween.
- `reconcileChildren`: keys kept are updated in place, removed keys wait for `remove` before unmount, order follows the items.
- Changing a text's content marks its relayout boundary dirty; layout runs once before the next render; changing `transform`, `zIndex`, or a colour does not run layout.
- A component constructed outside a tree touches no service; mounting registers, unmounting unregisters (spy on the context services).
- `screenBounds` and `screenToLocal` agree with the rendered position under nested offsets and a rotated transform.
- Callback timing: `onChange` sees the updated value; `setValue` from inside `onChange` does not re-fire; `consume()` in `onClick` stops the bubble.
- Screen switch: after navigating away, no input reaches the old screen's components; `onLayout` fires once on the new roots before the first render.

## 8.10 Conformance checklist

| Item | Level |
|---|---|
| Single interface for leaves and widgets, including design-system primitives | required |
| Properties of R8.2 with propagation rules and `pointerEvents` | required |
| Insertion-ordered children, parent back-reference, never reordered, state-preserving moves | required |
| `removeChild` unmounts | required |
| `reconcileChildren` | recommended |
| Margin-box bounds (per-side margin), content-box hit test with half-open edges, ink overflow with `inkExtent` | required |
| `transform` ignored by layout, honoured by render and hit testing | required |
| Read-only `screenBounds` and conversions; no window reads | required |
| Mount and unmount with a mount context; no constructor-time registration | required |
| Frame order: input with layout on demand, update on request, layout, render, snapshot | required |
| Clock and animator with tweens, reduced motion, retargeting | required |
| Upward invalidation to relayout boundaries; the non-invalidating property list | required |
| Overlay service owning overlay roots; roots sized from the viewport; `onLayout` | required |
| Named-argument constructors, accessors, synchronous callbacks | required |
| Per-component draw caches and retained draw lists | optional |
